# Native dependency probe

`cargo xtask native-probe` answers one question per target image: which version of each native library would a build
or a run find there, and does it meet the floor the crates declare? The plan asks for it in "Distribution and
toolchain" ([design/rust-compositor.md](../../design/rust-compositor.md)) as the Phase 0 dependency-floor audit.

| File              | What it is                                                                                                                                                                                                                 |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `libraries.toml`  | the libraries, each with the crate and build-file line that makes it a need, its pkg-config modules and shared objects, its floor and where the floor comes from, and the packages that provide it for each package family |
| `results/ID.toml` | one probe of one image: the version found per library, how it was read, and the run record (date, instance, command lines, exit codes)                                                                                     |
| `MATRIX.md`       | the stored reports as tables, generated by `cargo xtask native-probe matrix`; the xtask test fails when it is stale                                                                                                        |

## Run it

On an Agent37 instance, as root, from the repository root, with a built `xtask`:

```sh
cargo build -p xtask
sudo XTASK=target/debug/xtask scripts/native-probe.sh debian-12
```

`scripts/native-probe.sh ID` unpacks the image with `scripts/oci-rootfs.py` (no container runtime is needed), installs the
table's packages for the image's family inside it with `chroot`, reads the root file system with
`xtask native-probe check`, writes `results/ID.toml` and deletes the root. An image that cannot be unpacked gets a report
that says so and why. NixOS has no root to install into: the nixpkgs attributes are evaluated with the image's own `nix`.

Then regenerate the tables:

```sh
cargo xtask native-probe matrix > tests/native-probe/MATRIX.md
```

## What a status means

- `ok`: found, and at least the floor.
- `below-floor`: found, and older than the floor the crates declare. A build against it fails or loses a feature.
- `recorded`: found, and no crate declares a floor, so the version is recorded and nothing is judged.
- `unjudged`: found, but its version could not be read and a floor wants one.
- `missing`: no pkg-config file, no shared object and no package after the install.

A `mutter` line beside a library is the same judgement against the floor the Mutter product needs (libinput 1.30,
wayland 1.25, PipeWire 1.4.11). It is a comparison only: the rewrite removes those floors.

## What it cannot say

- The probe reads files. It does not start a driver, so GLES 3 and Vulkan 1.1 support are capabilities of a device it
  cannot see; the `egl-gles` row records Mesa's loader and the `gbm` row carries Mesa's version.
- It runs under gVisor on an Agent37 instance, without `/proc`, a kernel of the image's own or a GPU.
- A package the table names for a family may be called something else on a release the table was not checked against.
  The report lists it as absent, and the library shows `missing`; that is a finding about the table or the image, and the
  report's `packages-not-installed` says which.
- It never builds the workspace on the image. A floor that holds is not a passing package gate: the gates in
  `packaging/targets.json` (package build, install, login, removal) are separate.
