# Configuration reload: what each setting does at runtime

Beads `gnoblin-d5n` asks that every configuration change take effect without logging out, or
say plainly that it does not. This page is the audit that answers it, setting by setting. The
same classification is code (`crates/gnoblin-config/src/apply.rs`), and
`crates/gnoblin-config/tests/apply.rs` fails the build when a setting has no rule or when this
table disagrees with the rules.

## How a reload flows

1. `gnoblinctl config reload` (or `gnoblin.runtime.reload_config()` from a script) makes the
   runtime role evaluate `init.lua` again and validate the result.
2. A valid document is committed to the compositor (`config.commit`). A refused one is
   rejected (`config.reject`), the runtime keeps its last accepted document, and the caller is
   told which file and line.
3. The compositor applies the document in `Server::commit` (`crates/gnoblin-compositor/src/ipc/server.rs`):
   it publishes the `settings` object, pushes each live setting to the Wayland loop through
   `ControlHandle`, reconciles the X11 session, and records the document so the guardian
   reconciles autostart (`Guardian::reconcile_autostart`).
4. The reply carries the revision.

## What the status words mean

- **live**: the owning process applies the new value as soon as the document is accepted.
- **restart**: the owning process reads the value once, when it starts. The reload accepts the
  document, keeps the old behaviour and reports the setting as `restart required`. The
  process named in the row is the one that has to restart; restarting it alone is enough.
- **unused**: nothing reads the setting. The reload reports a change to it as `no effect`
  rather than letting it pass as applied.

## Which document a process started with

A setting read at start is compared with the document the process read, not with the previous
reload, so a setting changed and changed back is not pending.

- The compositor reads the last accepted file when it starts, before the runtime has committed
  anything. That file is the previous session's document, so a setting edited between two
  logins is reported on the first commit of the new session. Before this change the compositor
  ran on the old value and nothing said so.
- The services role and the compatibility host start after the runtime's first commit and
  read what that commit saved, so their baseline is the session's first accepted document.
- A child that crashes and restarts reads the newest saved document and so picks a pending
  change up early. The report can then name a setting that already applies; it never hides
  one that does not.

## Why the restart rows are not made live here

`compositor.renderer` and `capture.secure-treatment` choose the backend's renderer; replacing it
means recreating every GPU resource and capture in flight. `protocols` and `workspaces` change
what clients and the shell have already seen. `logging.*` and the services rows belong to
processes that read their settings before any document exists. Each of those would have to
restart the owning process, which is a guardian feature (restart one child with its effects
stated) and not a property of the reload; until it exists the reload says `restart required`.
