## 6. No-shell fallback (risk to step 5 and step 7)

`crates/gnoblin-wm/src/wm.rs` lines 93-96 define `FALLBACK_CASCADE_OFFSET = 32` and `FALLBACK_CASCADE_STEPS = 32`. Lines
1307-1325 place windows in a cascade when no shell is running, from (32, 32), stepping 32 px per visible window on each
output and workspace (commit `489a0cace`).

Risk: deleting `gnoblin-wm` removes this. It must move to a small module in `gnoblin-compositor` first (lane L0), with a
test that reproduces the cascade positions, so the no-shell start still places windows.

Resolved (lane W5): the module is `crates/gnoblin-wayland/src/fallback.rs`, not `gnoblin-compositor`, because `state.rs` calls it and `gnoblin-compositor` depends on `gnoblin-wayland`, not the other way round. F1 is amended to the minimal fallback (`node-core.md` F1): cascade placement, direct state requests, click-to-focus and raise. The owner's question timed out and defaulted to the recommended option, so this is a default selected, and the owner may revisit.

W4 status (lane W4, done): the five protocol files no longer name `gnoblin_wm` for a toplevel request. `xdg_shell.rs`, `zwlr_foreign_toplevel_management_v1.rs`, `xdg_activation_v1.rs` and `extension.rs` name a `WindowRequest` and hand it to `State::window_request` (`gnoblin-wayland/src/window_request.rs`). While a shell holds the tree and the session is not locked that is a `tree.event` `request` on the window's node: `maximize`, `unmaximize`, `fullscreen`, `unfullscreen`, `minimize`, `unminimize`, `close`, `raise`, `lower`, `activate` (`TreeRequest`). The shell answers by writing the node's `maximised`, `fullscreen`, `minimised`, `width` and `height`, and `State::answer_window_writes` turns them into the toplevel's configure (states, size, suspended); the shell's `window:close()` call is run by `State::run_window_calls`. While the shell holds the tree the three flags are read from the node (`State::effective_state`): the configure, the foreign-toplevel list and the node publish all use it, so the window manager's copy never overwrites the shell's. With no shell, `window_request_directly` applies the request through the window manager exactly as the protocol files did (the only remaining `gnoblin_wm::Event` uses are in that module and in `state.rs`, which W5 deletes). The `xdg_activation_v1` refusal is KEEP in the compositor: `refuse_activation` records the denial and no longer asks the window manager anything (its `ActivationDenied` effect only logged). Not done in W4, with the reason: `zwlr_layer_shell_v1.rs:402,446` (`OutputReserved`, the layer registry) is not a toplevel request, it feeds the window manager's work area for the no-shell path and the bar registry, and it goes with `state.rs` in W5. Only Wayland toplevels take the shell path: an X11 window's requests (from the IPC `window.set_*` calls, since X11 has no maximise, fullscreen or minimise request handler today) still go to the window manager, because nothing yet configures an X11 window from its node. Open: tiling and strip layouts still give a minimised window its slot (`Window:minimise` hides it but the layouts count every child), and `Window.visible` written by Monocle undoes the hide; the old layout engine excluded minimised windows, so this is a FLAG GAP for the layout modules, not for W4.

The paint order is the composer's (`Composer::window_stack`, the scene's depth-first order while a shell holds the tree) and the focus is `State::focus`; the record is given both as a `Standing` and keeps neither. While a shell holds the tree (`shell_places`) the record is only kept current: `apply_decided` drops its configures, stacking and focus and keeps only a window's presence on the outputs, and window nodes receive `enter`, `motion`, `leave`, `press` and `release` so the stock shell's focus policy runs on the real compositor.
