# JS shell parity audit: what Lua does that JavaScript does not yet do

Audited tree: lane JsParityAudit at `805fc4c7f` (branch `js-JsParityAudit`). Read-only audit: nothing was built or run, so every `done` rests on
reading the JS source and the named test, not on running it. Lanes that were still running (JsLock, JsXr, JsFlakes) are not in this snapshot;
`unverified` marks anything I did not read. Design decisions are `design/js-runtime.md` J1-J9. J9: Lua stays the reference until JS passes the
same corpus, then Lua is deleted.

Path abbreviations: `S/` = `data/lua/gnoblin/shell/`, `N` = `data/lua/gnoblin/node.lua`, `J/` = `data/js/gnoblin/`, `G` = `crates/gnoblin-js/js/gnoblin.ts`,
`T/` = `crates/gnoblin-js/tests/`, `LT/` = `crates/gnoblin-lua/tests/lua/` (case files `*_test.lua`), `RT` = `crates/gnoblin/tests/js_shell.rs` (real compositor).
Status words: `done` (file + proving test), `partial`, `not ported`, `dropped` (by decision), `native` (needs compositor/schema work first).

## Findings that block deleting Lua

1. **The JS shell still ran inside the Lua host (resolved by lane JsOwnConfig, see "JS-owned runtime role" in `design/js-runtime.md`).** Until then `crates/gnoblin/src/main.rs` called `gnoblin_lua::RoleRunner::run_with_js` and `GNOBLIN_SHELL_VM=js` swapped only the shell VM; the Lua host located and evaluated `init.lua`, validated and committed the whole config document, answered `config.reload` and sent the guardian's `autostart` list (`crates/gnoblin-lua/src/role.rs:1-60`), `crates/gnoblin-config/src/locate.rs` accepted only `init.lua`, and `crates/gnoblin-services/src/keyring.rs` read `init.lua`. Now `gnoblin_js::JsRoleRunner` does all of it: `locate` finds `init.ts`, then `init.js`, then `init.lua`; the role commits the document, serves `config.reload`, sends `autostart` and `config-accepted` to the guardian, and the services role decides `keyring.enabled` from the evaluated `init.ts`. `GNOBLIN_SHELL_VM` unset or `js` runs it, and `lua` runs the Lua role for one more release (an `init.lua` with no `init.ts` keeps the Lua role, with one warning). What is left for deleting Lua is step 8 and the Lua-only docs (step 7).
2. **Client window requests were dropped (resolved by lane JsClientRequests, see "Client requests status" in `design/js-runtime.md`).** The compositor sends `request` events (`maximize unmaximize fullscreen unfullscreen minimize unminimize close raise lower activate move resize menu`) and "changes nothing until
   the shell answers" (`crates/gnoblin-schema/schema/tree/messages.toml:169-178`). Only `menu` has a JS handler (`J/menus.ts:692-696`, the sole `onUiRequest` user). A client's fullscreen,
   minimise, close-request or activate did nothing under the JS shell; `J/window_state.ts` now answers every kind and `ClientListener.onRequest` lets a script answer first.
3. **Not ported at all:** lock screen, XR room, keyboard move/resize, reduced motion, the four gesture actions, `gnoblin.on` for arbitrary signals, and the whole
   host API outside the tree (session, process, idle, privacy, settings, find; outputs and per-output desks are done, lane JsOutputs, "Outputs status" in `design/js-runtime.md`). Details below.
4. **Behaviour differences a user sees (resolved by lane JsClientRequests: four workspaces by default, every matching rule merges, rules re-apply on appId, title and focus changes, fullscreen covers the whole output and the bars give way):** the stock workspace count (Lua: 4 in `data/default-config/config/10-windows.lua`, 9 when none declared, `S/init.lua:119-131`; JS: one `desktop`, `J/config.ts:519-524`);
   rules semantics (Lua merges every matching rule; JS first match wins unless `all: true`; Lua re-applies on any input change, JS only with `reapply`); fullscreen covers the screen minus bars in JS (`G:2324-2347`, `screenArea` `G:1575-1596`) but the whole output in Lua (`S/init.lua:774-778`).
5. **Types promise what the runtime lacks (outputs resolved by lane JsOutputs: `gnoblin.outputs` is a live `Collection<Output>`; `Output.apply` is not declared because the compositor has no operation behind it):** `crates/gnoblin-js-types/static/gnoblin-stock.d.ts` declares `readonly outputs: Collection<Output>` on `gnoblin`; `class Gnoblin` (`G:2585-2655`) had `clients workspaces input dialogs spawn show after` only.

**Migrator recommendation (not implemented):** do not write a general `gnoblinctl config migrate`. The shell files (`shell.lua`, `shell/*.lua`) are arbitrary Lua over the object model and cannot be converted
mechanically. A narrow converter for `gnoblin.configure{...}` literals and `shortcuts` is the only cheap part (a Lua table literal to a TS object literal, kebab keys to camel, `<Super>x` chords to `Super+x`), and `gnoblinctl check` already
rejects the retired names with the mapping in the message (`config.ts:454-459`). Better value: a written migration page with the table above, and a one-shot `gnoblinctl config init --from-lua` that reads the user's evaluated document through the existing
Lua host (the document is already JSON) and writes `defineConfig({...})` for the sections, plus a comment block listing unmapped constructs. Only worth building if there are users with `init.lua` files other than the shipped default; the owner should say.
The shipped starter (`data/default-config`) needs no converter: replace it.

## (d) Recommended cutover order

Each step lands alone and keeps the tree green. Acceptance is a check that fails before the step.

1. **Close the shell gaps that change daily use.** Client requests (`maximize unmaximize fullscreen unfullscreen minimize unminimize close raise lower activate move resize`), minimise focus hand-off, fullscreen over bars (`sync_fullscreen`), fullscreen sibling stacking, rule merge semantics decision. Acceptance: JS twin of `LT/states_test.lua` (12 cases) and the `shell_test.lua` raise/fullscreen cases pass in `T/`, plus one `RT` test where a real client's fullscreen request is granted.
2. **Decide and finish what needs native work first.** `parent_window`, `from_launcher` in `window.toml` (done); per-output `Screen` handling (unplug/park/reconnect, `move_to_output`, per-output workspaces and sets, done by lane JsOutputs); a Rust lock fallback (popups-portals.md row 9) and the JS lock screen; reduced motion; keyboard move/resize; the four gesture actions. Acceptance: JS twins of `shell_test.lua` unplug/dialog/output cases, `reposition_test.lua`, `gestures_test.lua` tail; lock: `RT` test that a session lock with no JS shell still accepts a password.
3. **Land XR on the JS side (lane JsXr).** Acceptance: a JS twin of `xr_test.lua` ring cases and `scripts/xr-smoke.sh` pointing at JS.
4. **Fix the declared-but-missing surface.** Either implement `gnoblin.outputs` (done) and the host objects the d.ts declares (outputs, session, process list, `on` for schema signals, `timers.now`) or remove them from `gnoblin-stock.d.ts:1315`; add a `workspaceSets` key.
