# Native std port: ending the hand-written SDK trees

Status: design only, written by lane NativeArch against `origin/rust-compositor` at `9d20a9a6d`. No code changes come with it.

It extends `design/modular-framework.md` (sections 4, 9, 10, 11, 25 and 31 to 38) and does not repeat it. Claims read from the
tree were checked with grep, `wc` and a read of the file. Claims about behaviour that was not run are marked `[INFERENCE]`.

The owner's decision, which this file carries out: `data/js`, `data/python` and `data/lua` must not exist.

Every behaviour of the stock desktop is native Rust in `gnoblin-std-impl` or `gnoblin-core-impl`. That covers layouts, scene
and cameras, the UI toolkit, XR, style, gestures, menus, panels, the launcher, the lock card, the overview, host glue, the
display manager, transitions and frame parts.

Every language SDK (Rust, Python, TypeScript and JavaScript) is generated from the catalog by one generator, and no generated
file is committed. Only starter shells, which are user-level programs and not an SDK, are hand-written. They live outside
`data/`.

## 1. The end state in one page

What is in the tree after the last lane:

- **Native libraries own all behaviour.** `libgnoblin-core.so.1` owns the object model every shell needs (collections,
  clients, outputs, operations, processes, idle, launches, dialogs, authentication, devices, input contexts and bindings).
  `libgnoblin-std.so.1` owns the desktop (workspaces, layouts, policy, style, scene, displays, UI toolkit, window frame,
  menus, shell parts, lock screen, XR).
- **One object protocol.** Both libraries serve classes, properties, methods and signals from a catalog through one small
  object API (section 4.2). A new class is a catalog file plus a Rust implementation. It needs no new table function and so
  no `abi.lock` edit.
- **One generator** (`gnoblin-sdkgen`, a library crate) renders every SDK. It runs from `build.rs` where a build embeds the
  result, from `cargo xtask dist` where an install needs it, and from `cargo xtask gen-sdks` for inspection and `--check`.
- **Nothing generated is committed.** Rust SDK sources land in `OUT_DIR`. The JavaScript and Python modules are embedded in
  `libgnoblin-runtime-js.so` and `libgnoblin-runtime-python.so`. Editor declarations (`.d.ts`, `.pyi`) are installed under
  `share/gnoblin/types/`.
- **Shell code stays shell code.** A custom layout, a drag binding, a gesture or a widget handler is a closure or a subclass
  in the shell's language. The native library calls it back through the callback ABI (section 5).
- **No shipped script is part of the SDK.** `share/gnoblin/js` and `share/gnoblin/python` stop existing. The default shell
  moves to `shells/default/shell.ts` and is installed as `share/gnoblin/default-shell/shell.ts`, as today.

### 1.1 Principles

1. **Behaviour is Rust, bindings are generated.** If code decides something, it is native. If it only spells a native
   thing in a language, the generator writes it.
2. **A shared body, never a copy.** Logic that names no language lives once in a native library. A runtime converts values
   and calls closures, nothing else.
3. **The catalog is the only description of a surface.** The std table is described by `object_verb` naming today. After
   lane NpObjectAbiA it is described by catalog files, and the table names are attributes of them.
4. **Parity is proved, not asserted.** Each lane records the old TypeScript behaviour as a golden before it deletes the
   code. The same lane proves the native path from a Python shell as well as a TypeScript one. A Python shell never had the
   TypeScript toolkit, so a passing Python test cannot be satisfied by a leftover script.
5. **The hand-written module is deleted in the same change** that lands its native replacement, unless another hand-written
   module that has not been ported yet still imports it. Section 6.2 lists those modules (an import-graph audit found them)
   and names the lanes that delete them, chiefly NpFlip. Until then they keep working through three small seams (6.2).

### 2.3 Challenging every shim

The assignment asks what must stay as a runtime shim. The answer is that no hand-written script survives. Each candidate
is Rust in the runtime crates, or generated.

| Shim today                                           | Can it be Rust in the runtime crate? | Verdict                                                     |
| ---------------------------------------------------- | ------------------------------------ | ----------------------------------------------------------- |
| JS `export * from "gnoblin-core/host"` append        | Yes                                  | `loader.rs` builds the synthetic module namespace           |
| JS import map (`gnoblin-core`, `gnoblin-std/<path>`) | Yes                                  | A fixed table in `loader.rs`: three specifiers (3.4)        |
| JS frame entry, dispatch queue, `wake.ts`            | Yes                                  | Gone: core `dispatch` and `wake_fd` already own it          |
| JS host bridge (`bridge`, `contract`, `*_bridge`)    | Yes                                  | Deleted: the runtime calls the object protocol directly     |
| JS `errors.ts`, `native_object.ts`                   | Generated                            | Error classes and the base class come from the catalog      |
| JS console rendering (`inspect.ts`)                  | Yes                                  | `gnoblin-js/src/console/inspect.rs`                         |
| JS bytecode of stock modules                         | Yes                                  | Optional build step (decision O13), no shipped file         |
| Python `_loader.py` (isolated generations)           | Yes, with PyO3                       | `loader.rs`: compile, purge, restore `sys.modules`          |
| Python `_runtime.py` (log routing)                   | Yes                                  | A `#[pyclass]` stream and `excepthook` in `logging.rs`      |
| Python `_base.py` descriptors, `api.py`, `events.py` | Yes                                  | `#[pyclass]` descriptors and the singleton in Rust          |
| Python `errors.py`, `_native.py`                     | Yes                                  | Exceptions are already created by the runtime               |
| Python `_std_base.py`, `_std_sugar.py`               | Generated                            | Conversion is `std_native.rs`; sugar is a catalog attribute |
| Python package import path                           | Yes                                  | A `sys.meta_path` finder serving the embedded modules       |

Two judgement calls:

- **The Python loader.** It manipulates `sys.modules`, compiles from source each time and restores state on failure. All
  of that is documented CPython API reachable from PyO3 [INFERENCE: not prototyped]. If the lane finds a piece that cannot
  be written in Rust, the fallback is a text constant inside `gnoblin-runtime-python`, not a file under `data/`. That
  fallback needs the owner's approval (decision O11).
- **JS classes the shell extends.** `Layout`, `Box`, `PointerDragBinding` and the rest are generated JavaScript classes
  over native handles. They are not shims: the generator writes them from the catalog, and they are embedded.

### 2.4 `data/lua` is dead: the proof

`data/lua` (23 files, 5,604 lines) is the node-core Lua shell of the retired `gnoblin-lua` runtime. The evidence:

1. The Rust consumer is gone. `CHANGELOG.md` records "The Lua shell and the Lua API are removed (lane JsDeleteLua)", with
   the crates `gnoblin-lua`, `gnoblin-lua-sandbox` and `gnoblin-lua-pattern` and the `mlua` dependency deleted.
   `grep -rn 'mlua\|rlua\|piccolo' --include=Cargo.toml .` finds nothing, and `crates/` has no Lua crate.
2. The only reader of the tree is `cmake/install-lua-data.cmake`, which copies `data/lua/` to `share/gnoblin/lua`. It is
   included from `cmake/install-session.cmake:179`. Commit `aec6b7d91` restored the files for the frozen legacy C tree
   (decision D9 of the Lua removal).
3. The legacy C Lua runtime does not load them. `src/config/lua/*.c` implements its own `gnoblin.*` API in C and sets no
   `package.path` for `share/gnoblin/lua`: `grep -rn 'package.path\|share/gnoblin' src/config` finds no such path, and
   `grep -rIn 'gnoblin\.shell\|gnoblin/node\|share/gnoblin/lua' src cmake tests scripts` finds only the C API's own
   `gnoblin.shell.ping()` strings in `tests/lua-api-test.c`, which are C-registered functions.
4. Every other reference is a comment or a changelog line. The ports in `data/js/gnoblin-std/{alerts,focus,gesture_actions}.ts`
   cite the Lua file they came from, and `tests/shell/placement_cases.toml` (kept, it is a JS test fixture) names
   `floating.lua` in a comment.

Lane NpLuaDelete removes the tree, the cmake install script and its `include`, and the text of decision D9 that froze it. It
proves the claim with the commands above, the legacy CMake install test and the `lua-runtime.yml` job.

Out of scope: `data/default-config`, `data/init.lua.example` and the C Lua runtime. The owner named only `data/lua`.

## 3. Generation, end state

### 3.1 One generator, three call sites

A new library crate `crates/gnoblin-sdkgen` takes over `xtask/src/sdk/` (7,830 lines: `model`, `rust`, `std_dyn`, `python`,
`python_std`, `typescript`, `typescript_std`, `verbs`, `layouts`, `text`). `xtask` keeps only the commands.

- **Sources:** the catalog files (section 4.3), the reflection of `gnoblin-core-abi` and `gnoblin-std-abi`, and
  `gnoblin-std-abi::layouts`.
- **Dependencies:** `gnoblin-schema`, `gnoblin-core-abi`, `gnoblin-std-abi` and `gnoblin-types`. It must not depend on
  `gnoblin-core`, `gnoblin-std`, `gnoblin-std-dyn`, `gnoblin-js` or `gnoblin-js-types`, which consume its output.
  `xtask/src/deps.rs` gets a rule for it: a build-dependency of the SDK, runtime and `gnoblinctl` crates only.
- **Determinism:** the generator reads no clock, environment or locale and orders everything by name. Two renders are byte
  identical, and `--check` proves it.
- **Formatting:** build scripts do not run `rustfmt`. `gen-sdks --out` does, so the output a person reads looks like source.

The three call sites:

| Call site                                    | When           | What it does                                                         |
| -------------------------------------------- | -------------- | -------------------------------------------------------------------- |
| `build.rs` of an SDK or runtime crate        | Every build    | Renders that crate's targets into `OUT_DIR` and writes `embedded.rs` |
| `cargo xtask dist install`                   | Install        | Renders the `types` and `c` targets into the prefix                  |
| `cargo xtask gen-sdks [--out DIR] [--check]` | By hand, in CI | Renders everything to `target/sdk` for reading, or checks            |

### 3.3 Embedding and loading

**JavaScript.** `gnoblin-js/build.rs` calls the generator and writes `OUT_DIR/stock.rs`:

```rust
pub static MODULES: &[(&str, &str)] = &[("gnoblin-core", include_str!("gnoblin-core.js")), /* … */];
pub const CATALOG: &[(&str, u64)] = &[("gnoblin", 0x0), ("gnoblin.model", 0x0), ("gnoblin.std", 0x0)];
```

`gnoblin-js` exposes `Stock::embedded()`, and `loader.rs` resolves the three specifiers against `MODULES`. The modules are
plain JavaScript, so oxc and stock source maps leave the stock path.

At start, the runtime compares `CATALOG` with the core's `gnoblin_catalog_hash()` and with the std library's hash. A mismatch
refuses the shell with a message naming both hashes, which protects a core upgraded without its runtime.

**Python.** `gnoblin-runtime-python/build.rs` does the same for `py` and writes a table of module names and sources. At
interpreter start the runtime puts a finder on `sys.meta_path`. It is a `#[pyclass]` whose loader runs the embedded source.
User modules beside the script keep going through the isolated loader, now Rust.

**Rust.** The SDK crates `include!` the generated file. For the publishable crates (decision D19) see 3.8.

**Why embed, not install.** A generated module is tied to a catalog hash. Installed files can drift from the library that
serves them, for example when a package upgrade replaces one and not the other. An embedded module cannot. Embedding also
removes `share/gnoblin/js`, `share/gnoblin/python`, `GNOBLIN_JS_STOCK_DIR` and `GNOBLIN_PYTHON_DIR`. The cost is that stock
modules cannot be patched on an installed system (decision O2).

### 3.4 How an import resolves

| Language       | Spelling                                             | Resolves to                                                                                                                      |
| -------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| JS or TS       | `from "gnoblin-core"`                                | The embedded module, always available                                                                                            |
| JS or TS       | `from "gnoblin-std"`                                 | The embedded module. Evaluating it opens `libgnoblin-std.so.1`, or throws `gnoblin-std is not installed (looked in: …)` as today |
| JS or TS       | `from "gnoblin-std/xr"`                              | The embedded optional XR module. The only subpath                                                                                |
| JS or TS       | any other `gnoblin-std/<path>` or `gnoblin/…`        | An error naming the three valid specifiers (decision O3)                                                                         |
| Python         | `from gnoblin import gnoblin`                        | The embedded package over the core object API                                                                                    |
| Python         | `from gnoblin.std import …`                          | The embedded module. Without the library: `ImportError: gnoblin-std is not installed (looked for libgnoblin-std.so.1 in …)`      |
| Rust           | `use gnoblin_core::…`, `use gnoblin_std::prelude::*` | The SDK crates, generated files in `OUT_DIR`                                                                                     |
| TS editors     | the TypeScript spellings                             | `tsconfig.json` `paths` map to `share/gnoblin/types/*.d.ts`                                                                      |
| Python editors | `gnoblin`, `gnoblin.std`                             | `share/gnoblin/types/python/`, a stub-only package with `py.typed`                                                               |

Example 17 (std absent) keeps its behaviour. A core-only shell never evaluates `gnoblin-std`, and a shell that imports it
without the library fails with the same text.

### 3.5 TypeScript declarations

- **Source.** `types` renders one `.d.ts` per module from the catalog. Properties carry the catalog documentation as JSDoc,
  enums become string-literal unions, interface classes become abstract classes, and records become interfaces.
- **Install.** `cargo xtask dist` writes `share/gnoblin/types/{gnoblin-core,gnoblin-std,gnoblin-std-xr,globals}.d.ts`,
  `tsconfig.json` and `python/`. `gnoblin-js-types` stops embedding library sources and moves into `gnoblin-sdkgen` as the
  `types` target, keeping the tsconfig rendering.
- **`gnoblinctl types init DIR`** writes the same files from the copy embedded in `gnoblinctl`, so a user without an
  installed prefix still gets them. Go-to-definition opens a `.d.ts`, no longer the library source.
- **`gnoblinctl config check --types`** writes the embedded declarations to its scratch directory with a `tsconfig.json` whose
  `paths` name them, and runs `tsc` as it does now. The dry-run host that evaluates the module uses the embedded modules and
  the real object protocol over an empty compositor.
- **In the repository,** `scripts/js-typecheck.sh` runs `tsc` over the starter, the examples and the golden scripts against
  the generated declarations. It no longer type-checks a library.

### 3.6 Proving stability when outputs are not committed

Today `gen-sdks --check` proves the committed files are current. That check disappears with the files. What proves
stability instead:

1. **`abi.lock`, unchanged.** It pins the C ABI of both libraries. The object protocol adds one function to each table and
   one shared struct, once (section 6.1).
2. **`surface.lock`, new.** The generator renders the public surface of every catalog class as sorted lines, one per member:

    ```text
    member | gnoblin.std | box.padding | property insets rw | 0.2.0
    member | gnoblin.std | menu_item.run | property callback rw | 0.2.0
    ```

    `cargo xtask gen-sdks --check` compares them with the lock files the way `abi-check` does. A removed or changed entry
    that a release covers fails. An addition is recorded with `--update`. The lock is one file per catalog module
    (`crates/gnoblin-std-abi/schema/lock/<module>.lock`), so two lanes that add classes to different modules edit different
    files and never conflict.

3. **Determinism.** `--check` renders twice and compares the bytes.
4. **Validity.** `--check` runs `python3 -m py_compile` over the Python modules, `tsc --noEmit` over the declarations and a
   Node parse of the JavaScript when `node` is present. Cargo checks the Rust output.
5. **Two-way completeness.** A test in `gnoblin-std-impl` and one in `gnoblin-core-impl` fail when a catalog class has no
   implementation, or an implementation names no class. It is the check `inert_surface` makes for tree properties.
6. **Golden shells, unchanged.** `tests/modular/golden` keeps three prebuilt native shells and `golden.lock`, run by
   `abi_upgrade.rs` against the current and the next-minor libraries. They are the binary proof.
7. **Golden scripts, new.** `tests/modular/golden-scripts/{shell.ts,shell.py}` use a recorded set of released catalog
   members and have a recorded trace of tree writes and events. They run against freshly generated SDKs on every CI run. A
   generator change that alters the meaning of a released member changes the trace and fails.
8. **Declaration compatibility, transitional.** NpOracle commits `tests/ts-compat/old-surface.d.ts`, the declaration emit of
   today's TypeScript library, and `compat.ts`, which asserts that each class of the new `gnoblin-std.d.ts` is assignable to
   the old one. NpGate deletes both after the owner signs off the new surface.

`just gen-sdks-check` runs items 2 to 5. The workflow job `gen-sdks` keeps its name.

### 3.7 Developer loop

- A catalog edit changes a generated file only inside `OUT_DIR`, which rust-analyzer reads. `cargo xtask gen-sdks` writes
  `target/sdk/` for a person who wants to read a generated file, and each file's banner says so.
- `cargo build` regenerates when a catalog directory, an ABI crate or the generator changes (`cargo:rerun-if-changed`). The
  added cost is unknown [INFERENCE]. NpGenOut measures it and fails its own acceptance above 20 s added to a clean
  workspace build on an a37 box.
- No stage step remains for scripts. `cargo xtask stage` keeps linking the libraries and runtimes and no longer needs a
  stock directory.

### 3.8 Publishing the SDK crates

D19 keeps the two SDK crates unpublished but publishable, and a `build.rs` that calls a path dependency cannot be published.

The rule: `cargo xtask publish-prep` renders the Rust target into the crate's `src/generated/`. That directory is listed in the
`include` of `Cargo.toml` and ignored by git. The build script uses it when it exists and skips the generator. Nothing is
uploaded; this only keeps the option open (decision O10).

## 4. The native object model: catalog and ABI

### 4.1 Catalog extensions

The catalog format is the one `gnoblin-schema` already parses:

- objects with `base` and `record`;
- properties with `readonly`, `animated` and `default`;
- methods, with `function` for a static one, signals, fields with `optional`, errors, and `since` on every member.

Lane NpObjectAbiA adds the rows below. Everything else in the format is unchanged.

| Addition                               | Meaning                                                                                                               |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `[schema] local = true`                | The namespace is served by a library, not the compositor. It is skipped by the wire and by the `gnoblin` catalog hash |
| `kind` on an object                    | `handle` (default), `record`, `interface`, `service`. `record = true` stays as an alias                               |
| `enum:<name>` type and `[[enum]]`      | A closed set of named values. Generators write string unions, `IntEnum` and Rust enums                                |
| `callback:<name>` type, `[[callback]]` | A closure a shell passes in: named parameters and a result. Used for handlers and `compute` functions                 |
| `interface` objects                    | Methods marked `required` or optional, with `default = "native"` when the library has a default body                  |
| Cross-namespace `base`                 | `base = "gnoblin.model.client"` lets std extend a core class                                                          |
| `ctor = [..]` on an object             | The constructor takes these properties (default: every writable property, by name, as an options record)              |
| `export = { js, py, rust }`            | A name that differs from the mechanical conversion (`snake_case` to `camelCase` and back)                             |
| `python = { dunder = "__len__" }`      | Maps a member to a Python special method, replacing `_std_sugar.py`                                                   |
| `inert = "reason"`                     | A member accepted and not applied. `inert_surface` reads these instead of two hand-kept lists                         |
| `abi = "fn:<table function>"`          | The member is served by an existing typed table function, until NpAbiClean folds it                                   |

### 4.2 The object protocol (one ABI change, batch B1)

Everything the lanes add after B1 is catalog and Rust, with no ABI edit. B1 adds:

- **Shared types** in `gnoblin-core-abi`: `GnoblinObj` (a `u64` handle, generation-tagged), `GnoblinClassId` and
  `GnoblinMemberId` (`u32`, resolved by name), `GnoblinInvokeFn`, and the struct `GnoblinObjectApi`.
- **New value kinds** appended to `GnoblinValue` (the schema's kinds are unchanged): `OBJECT` (a handle), `RECORD` (class id,
  field array, count), `CLOSURE` (`invoke`, `user`, `drop_user`) and `ENUM` (`uint`). A `list` may hold any of them.
- **One new function** in `GnoblinApi` and one in `GnoblinStdApi`: `object_api(ctx, namespace, out)`. The core serves
  `gnoblin.model`, std serves `gnoblin.std`, and both return the same `GnoblinObjectApi` layout.

```c
typedef int32_t (*GnoblinInvokeFn)(void *user, GnoblinMemberId member,
                                   const GnoblinValue *args, size_t n, GnoblinValue *out);
struct GnoblinObjectApi {
  uint32_t size, reserved;
  int32_t (*class_id)(GnoblinCtx, GnoblinStr name, GnoblinClassId *out);
  int32_t (*member_id)(GnoblinCtx, GnoblinClassId, uint32_t kind, GnoblinStr name, GnoblinMemberId *out);
  int32_t (*catalog_each)(GnoblinCtx, GnoblinCatalogFn cb, void *user);
  int32_t (*create)(GnoblinCtx, GnoblinClassId, const GnoblinInit *inits, size_t n, GnoblinObj *out);
  int32_t (*destroy)(GnoblinCtx, GnoblinObj);   /* ends the object and its children */
  int32_t (*release)(GnoblinCtx, GnoblinObj);   /* drops only the script's reference */
  int32_t (*get)(GnoblinCtx, GnoblinObj, GnoblinMemberId, GnoblinValue *out);
  int32_t (*set)(GnoblinCtx, GnoblinObj, GnoblinMemberId, const GnoblinValue *);
  int32_t (*call)(GnoblinCtx, GnoblinObj, GnoblinMemberId, const GnoblinValue *args, size_t n, GnoblinValue *out);
  int32_t (*call_static)(GnoblinCtx, GnoblinClassId, GnoblinMemberId, const GnoblinValue *args, size_t n, GnoblinValue *out);
  GnoblinReg (*listen)(GnoblinCtx, GnoblinObj, GnoblinMemberId signal, GnoblinInvokeFn, void *user, GnoblinDropFn);
  int32_t (*unlisten)(GnoblinCtx, GnoblinReg);
  int32_t (*implement)(GnoblinCtx, GnoblinClassId, const GnoblinImpl *, GnoblinObj *out);
};
```

Rules that carry over from section 5:

- Inputs are borrowed for the call. A `GnoblinValue` the library returns is valid until the next call on the thread, or
  owned and freed with `value_free`.
- **Lifetime.** An object lives until `destroy`, until its parent is destroyed, or until its generation retires. `release`
  drops the script's reference only. A widget a script lost the reference to stays on screen, as a canvas does today.
- The library never runs a closure inside `create`, `set` or `call`. A change announces itself from the next turn, so a
  handler cannot re-enter the call that caused it.
- **`GnoblinImpl`** is `{ size, implemented: *const u64 /* member bit mask */, invoke, user, drop_user }`. `implemented` tells
  the library which interface methods the shell defined, so an absent optional hook costs nothing and a stock default runs
  natively.

**Cost of a call, measured.** `what_a_call_costs` in `crates/gnoblin-std-impl/tests/object_protocol.rs` (`#[ignore]`d; run it with
`cargo test -p gnoblin-std-impl --release --test object_protocol -- --ignored --nocapture --test-threads=1`) times each call 200 000
times against an `entry_model` made through the C table, over a real core generation, in a release build on a 2-CPU Agent37 box. Two
runs agreed within about 10 per cent; each figure is nanoseconds per call, the range of the two runs:

| What is timed                                                                           | ns               |
| --------------------------------------------------------------------------------------- | ---------------- |
| An existing typed table function (the core's `stats`, which fills a struct)             | 38               |
| `get` of a number                                                                       | 64 to 72         |
| `get` of text (21 characters)                                                           | 100 to 127       |
| `set` of text                                                                           | 320 to 370       |
| A method with no arguments that changes nothing (`home`)                                | 200 to 220       |
| Two calls that each change the model, `insert` with a text and `backspace`, no listener | 770 to 810       |
| `class_id` or `member_id` by name                                                       | 16 to 24         |
| `listen` then `unlisten`                                                                | 220 to 260       |
| The turn when nothing is queued (`dispatch`)                                            | 220              |
| Two changing calls, two signals told into a closure, and a turn for those two alone     | 12 100 to 12 900 |
| The same with one turn for every hundred changes, per change                            | 790 to 855       |

What the numbers say:

- A property read is one table call and a conversion, about 30 ns over the cheapest typed function; a write of text or a method call
  is three to nine times the typed function, because the library checks the arguments against the catalog and copies the text. A shell
  can do a thousand calls in a frame for well under half a millisecond. Nothing here needs a bulk function in the table:
  `update(obj, inits)` writes several properties in one call, and a record answers every field in one `get`, for a lane that wants one
  crossing.
- What costs is the turn. A turn that has something to tell costs about 12 microseconds by itself (the library posts a turn when the
  first change is queued, and the dispatch runs it; the time is the two together and is not broken down further), and the same turn
  shared by a hundred changes costs under a microsecond for each. The library already posts one turn per generation and tells a
  property that changed several times in it once, so a lane that changes a thousand properties in one layout pass pays for one turn. A
  lane must not make a change and wait for its signal in a loop.
- Looking a class or a member up by name costs about 20 ns, a fraction of a call, so resolving every member of a class when it is
  first used (what the typed Rust API does) costs about a microsecond a class, once.
- Text is the dear value: a `get` of text is one and a half times a number and a `set` three to five times, and the text is copied each
  way. A lane that moves large amounts of text (paint lists, 4.x) passes one record or bytes value, not many small strings.

Not measured: a call from a script runtime (its own conversion of values is added to every figure above; NpObjectAbiB measures it with
the first generated classes), and the typed Rust API's own cost over the raw call (a cell check and the conversion of one `Val`).
Painting, hit testing, layout and cascade run inside the library without crossing.

**B1.1, landed with B1 as the one more change to `abi.lock`.** `GnoblinObjectApi` gained `track(ctx, cb, user)`, and a class may extend a
class the other library serves.

- `track` installs a tracker for the thread. Until it is cleared, every successful property `get` through that library's table calls
  `cb(user, obj, class, member)`. This is all the property-dependency hook of 5.6 needs, so `node.properties.bind` adds no table
  function: the core installs a tracker on its own table and on std's, runs `compute`, removes the trackers, and listens to each
  (object, member) that was read (`listen` already takes a property) and runs `compute` again when one changes. NpCoreModel writes
  that loop in `gnoblin-core-impl`; the typed client has `Api::track`, which returns a guard that clears the tracker when dropped.
- A class of `gnoblin.std` whose base class is one of `gnoblin.model` (`base = "gnoblin.model.client"`) lists the base's members first
  in its catalog, with the ids they have in the base. The derived library makes a base object in the core with its own, forwards `get`,
  `set`, `call` and `listen` of those members to it, and releases it with its own. A handle that a forwarded member returns belongs to
  the core's table, so the typed Rust API refuses at build time a base member whose type names a class of the other namespace; no
  lane needs one yet, and the first that does adds the second `Objects` to the typed handle.
- A property of a record may say `optional = true` (4.1): the typed Rust API reads it as an `Option`, and a field with neither a default
  nor `optional` is always there. The focus policy's records say which of their fields are which.

The tests are `crates/gnoblin-object/tests/protocol.rs` (an interface, a closure property, values of every kind, signals, the tracker
and a class with a foreign base, over two hand-written catalogs), `crates/gnoblin-object/fixtures/probe` (the catalog of one class of
every kind, rendered into tables and a typed API at build time and run against a library built on them), and
`modular::native_object` (example 20, in a real session).

NpObjectAbiA proves the protocol with a vertical slice before anything else is built on it: `toast` (section 4.4) from the
Rust SDK, from Python and from TypeScript, in a real session. If the slice shows a flaw, the protocol changes once, before
any other lane has started.

### 4.5 Naming and export rules

- Catalog names are `snake_case`. JavaScript and TypeScript use `camelCase` members and `PascalCase` classes. Python keeps
  `snake_case` and `PascalCase`. Rust follows its conventions.
- A static function a script imports by name (`focusDecision`, `edgeZone`, `placeCard`, `menuKeyAction`, `formatClock`,
  `onSwipe`, `onPinch`, `toast`, `openLauncher`) is exported by the generated module with the same name it has today.
  The catalog `export` attribute covers any that the mechanical conversion would spell differently.
- Constants that scripts read (`SNAP_MARGIN`, `REPOSITION_STEP`, `DIMMED_OPACITY`, `SWIPE_THRESHOLD`, `PINCH_THRESHOLD`,
  `REST_DELAY`, `REQUEST_DRAG_LIMIT_MS`, `CLOSE_FADE_MS`) are catalog constants.

## 5. Code a shell author writes, called back by the native std

### 5.1 The mechanism

All four cases use the same path. The shell passes a closure or an object that implements an interface, and the library stores
`{ invoke, user, drop_user }`.

The path is the callback ABI that exists today, and for every new interface the generic `GnoblinInvokeFn` of section 4.2:

- `GnoblinStdLayoutVtable` for layouts;
- `GnoblinStdDragFn` and `GnoblinStdGestureFn` for bindings;
- `GnoblinStdEventFn` for collection events.

- **Where it runs.** On the shell thread, from the turn of the shell's dispatch. The library never runs a callback inside a
  table call. The callback budget of section 31.1 applies: a callback that runs too long or throws earns a strike for the
  generation, as for any shell callback.
- **Who converts.** The generated trampoline of each language turns the `GnoblinValue` arguments into script values (lazy
  getters over records, handle classes over objects) and the script's result back into a `GnoblinValue`. The library sees
  only values. JavaScript keeps a per-context table of function references so a closure stays in its own heap
  (`runtime-js/src/std_native.rs`). Python takes the GIL in the trampoline.
- **Errors.** An exception becomes `E_PANIC` for that call, is logged with the script's traceback or stack, and the library
  carries on with the interface's default (for a layout, the previous placements; for a drag hook, a cancelled drag).
- **Defaults run natively.** `implemented` (4.2) lists the methods the shell defined. A method the shell did not define is
  never called across the ABI.
- **Reload.** Every registration belongs to the generation that made it and is dropped with it (`drop_user` runs once while
  the code is still mapped, D16). State that belongs to the library (workspaces, clients, style) survives, because the std
  context is not a generation's.

### 5.2 Custom `Layout` classes

```ts
class Spiral extends Layout {
    turns = 2;
    compute(cx: LayoutContext): Placement[] {
        /* rectangles from cx.area, cx.clients */
    }
}
workspace.layout = new Spiral();
```

- `Layout` is the generated base class of the catalog interface `layout`. It is the only extension point of layouts.
- Assigning it calls `workspace_set_layout` with `STD_LAYOUT_FOREIGN` and a vtable whose entries are the generated trampolines
  of the methods the subclass defined. `drop_user` releases the script object.
- The workspace driver (native) calls `compute` from its turn whenever the workspace is invalid: a client joined or left, the
  area changed, a gap changed, or `revision` moved. The context carries the area, the gaps and the clients as handles with
  their state. The answer is a list of placements written back natively, with the whole-pixel tiling the stock layouts use.
- The options are plain fields on the object, compared between turns, as they are today. A layout that changes by itself
  defines `revision`, otherwise the shell calls `workspace.invalidate()`.
- A script layout can use the stock arithmetic: `Builtin` layouts and `layout_ring` are standalone functions that need no
  workspace and do not start the desktop.
- Dividers (`find_split`, `set_split`, `reset_split`) let a script layout take part in split-resize drags.

### 5.3 `ClientResizeBinding`-style bindings

`ClientMoveBinding`, `ClientResizeBinding`, `ClientSwapBinding` and `SplitResizeBinding` are generated classes from
`BINDING_KINDS`. They extend the interface `pointer_drag_binding`.

- **Matching is native.** The input matcher moves to the core (NpCoreInput): chord, threshold, tiers (device, layout,
  context), priority, decline, click versus drag, scope, and cancel when the window closes. The std drag rules
  (`drag_step`, `drag_clamp`, `drag_resize`, `drag_zone`, `drag_tile`) are called by the matcher, not by script.
- **A stock binding makes no crossing.** `new ClientResizeBinding({ edges: "all" })` registers with an empty `implemented`
  mask. The matcher calls the rules directly and writes the geometry.
- **A subclass crosses only where it overrides.** If it overrides `onUpdate(event)`, the matcher calls it with the drag event.
  The default `super.onUpdate(event)` is the generated method that calls `drag_step` and applies its answer natively, so a
  script that "adjusts and delegates" keeps the rule and the write.
- **Hook names are kept:** `onStart` (answers whether this binding takes the drag), `onUpdate`, `onEnd`, `onCancel`. The state
  objects (`MoveState`, `ResizeState`, `SwapState`, `SplitState`) are records the native start returns and the hooks receive.
- **A binding of your own** is a subclass of `pointer_drag_binding` with its own hooks, or the function form
  `input.bind("Super+MouseLeft+Drag", (drag) => …)`.
- **Open item.** Section 34's note says the update, end and cancel calls of a closure drag were not observed reaching a
  TypeScript closure in one rig. NpCoreInput must prove the closure path from TypeScript, Python and Rust, including
  cancel-on-close, before it deletes `input/pointer.ts`.

### 5.4 Custom gesture triggers

- **Spellings, not grammars.** A trigger is a string (`Super+Return`, `Super+MouseLeft+Drag`, `Swipe3Left`, `Pinch2`). The
  grammar is `trigger.parse` in the core, one implementation for every language. A shell can bind any spelling the grammar
  accepts. A new kind of trigger (for example a new device class) is a catalog enum extension in the core, not something a
  shell adds.
- **Behaviour is an interface.** `gesture_binding` has `on_begin(event) -> bool` (take the gesture or decline it),
  `on_update`, `on_end` and `on_cancel`. The event is a record: kind (`swipe`, `pinch`), fingers, the movement since the start,
  the scale, the phase, and where the pointer was.
- **Stock actions are native.** `onSwipe({ left: "workspace.next", up: fn })` returns a `swipe_action_binding`. Named actions
  run natively. A function value is a closure called when the swipe ends far enough in that direction.
  `WorkspaceSlideBinding` follows the fingers natively, drives a transition, and finishes or reverses it.
- **Claims** are shared and handed over across a reload by the core, as `input/claims.ts` does now.

### 5.5 Widget event handlers and custom widgets

```ts
const button = new Box({ padding: 8, background: "#334" });
button.onPointer = (event) => {
    if (event.kind === "press") run();
    return true;
};
```

- A handler is a `callback` property or a signal listener on `canvas`. The native toolkit hit-tests, bubbles from the target
  to its parents and calls each handler through `invoke`. A handler returns `true` to stop the bubble, which replaces
  `UiPointerEvent.stop()`.
- Keyboard focus, `Tab` handling and `secure` canvases are native. A handler on a focused canvas receives `ui_key_event`
  records.
- **A custom widget** subclasses `Box` (or `Canvas`) and overrides `paint()`, `measure()` or `arrange()`. `paint()` returns
  a list of `paint_op` records that the library encodes (the encoding is Rust now, not script). The library calls `paint`
  only when the widget is dirty. A widget that overrides nothing is drawn entirely natively.
- Text measurement is synchronous in the library (`gnoblin-paint`), so `text.metrics` has no pending state. The answer is
  the one the compositor's painter would give, because both use the same crate.

### 5.6 Property bindings and predicates

- `node.properties.bind(name, compute)` takes a closure. The library runs it under dependency tracking (a native read of a
  property records the dependency), writes the result, and runs it again when a dependency changes.
- `where(query)` is native and takes a data-only record. A predicate function (`find(fn)`, `filter(fn)`) iterates in the
  language over `to_list()`, because a predicate cannot be evaluated without script.

## 6. Lanes

### 6.1 Sequence points and ABI batching

The ABI and the catalog are the shared files, so they set the order. Three rules keep `abi.lock` conflict-free:

1. **One batch, B1.** NpObjectAbiA is the only lane that edits `abi.lock`, `exports.txt` or the table structs before B1
   lands. B1 carries the object protocol of 4.2 and every other change the audit below can foresee. Nothing else is started
   against an unmerged B1.
2. **After B1, a lane adds catalog and Rust only.** A catalog edit changes `surface.lock`, which is one file per module. It
   never changes `abi.lock`. The `gnoblin` namespace fingerprint and the golden shells are untouched.
3. **A late ABI need goes through Main.** A lane that finds it cannot do its work without a table function stops, messages
   Main, and uses the closest catalog workaround meanwhile. Main collects the requests and asks the owner of NpObjectAbiA to
   land them as one commit, B1.1, at a wave boundary (the end of wave C and wave D below). No lane edits `abi.lock` by hand.
   NpAbiClean lands the last batch (B2): it removes the table functions and `tree_link_*` that no caller uses.

What the B1 audit checks before it merges, because a miss means a B1.1:

- Canvas pointer, key and focus delivery to a std library reaches it through `on_signal` or `subscribe` without a new function.
- Std timers register wakes through the core's `wake_fd` and `timer_add`, so `wake_sources` has a native subject.
- The input matcher in the core needs seat grabs, claims and pointer-button claims (`claim`, G4). They exist.
- A `GnoblinValue` record carries every field of `paint_op` and `lock_style` without a size limit.
- `GnoblinImpl.implemented` has room for 64 members per class and the protocol allows more by a second word.

The order, as a graph:

```text
S0  NpLuaDelete   NpStarterMove   NpOracle   NpGenOut          (disjoint files, all four in parallel)
S1  NpObjectAbiA  (B1)   ->   NpObjectAbiB
S2  wave C (additive native): NpStdUi  NpStdStyle  NpStdScene  NpCoreModel  NpCoreServices  NpCoreInput  NpPyRuntime
S3  wave D (needs a wave C lane): NpStdFrame  NpStdMenus  NpStdShellUi  NpStdXr  NpStdPolicy  NpStdObjects  NpStdDisplay
S4  NpFlip   (the one serial point: the TypeScript engine goes)
S5  NpJsFinal   NpTypesCtl   ->   NpAbiClean (B2)   ->   NpGate
```

At most four lanes run at once, because the quota is five boxes including the one the gate uses.

### 6.2 What the lanes may delete, and the three seams

The import graph of `data/js` (computed over every `from "gnoblin-…"` edge between its 230 TypeScript files) shows which TypeScript modules the
rest of the library imports. A module that nothing outside its own group imports can go in its lane. A module that the
engine's host glue imports goes at the flip.

| Deleted in the lane that replaces it                                            | Deleted at NpFlip (hand-written TypeScript still imports it)                                           |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| JS11 UI, JS12 frame, JS13 menus, JS14 shell parts, JS16 XR, JS9 scene, JC7 math | JC2, JC4, JC5, JS2 to JS8, JS10, JS15 at NpFlip; JC3 and JC6 at NpJsFinal, with the natives they serve |
| PY1 to PY3 (Python has no TypeScript importer)                                  | -                                                                                                      |
| LUA, JST                                                                        | -                                                                                                      |

Import counts behind the right column, as edges from other groups:

- the engine's `host/*` is imported 69 times by the std host (JS3) and 28 times by the std glue (JS4);
- the layout classes are imported 8 times by the workspace host;
- the binding classes are imported 7 times by the layouts and 4 times by the policy modules.

That is why the engine's object model cannot be replaced module by module.

While the engine is still TypeScript, three seams keep the rest working. All three are deleted by NpFlip, and none of
them is a new public API.

- **S1, handle conversion.** A generated class that takes or returns a client, output, workspace or collection converts
  through two functions of the generated JavaScript module, `fromNative(kind, id)` and `toNative(object)`. Until the flip they
  look the object up in the engine (`gnoblin.clients`, the TypeScript `Workspace`). After it they are the identity.
- **S2, interim re-export files.** When a lane deletes an implementation that hand-written TypeScript still imports, it leaves
  a file of one line (`export { Box } from "gnoblin-std/generated";`) whose first line is `// interim (NpStdUi): deleted by
NpFlip`. `grep -rl 'interim (Np' data/js` lists them.
- **S3, embedded generated modules under the old paths.** NpGenOut serves the generated modules from the binary under
  `gnoblin-core/generated/*` and `gnoblin-std/generated/*`. The rest still comes from `GNOBLIN_JS_STOCK_DIR`, which
  NpJsFinal deletes together with the directory.

The audit is the first deliverable of every lane: `grep` for importers of each file it means to delete, and anything found
moves to the right-hand column and is named in the lane's commit message.

### 6.4 The lanes

### 6.5 Parity gates and how each test is migrated, not weakened

Rules that every lane follows:

1. An assertion line is not edited. The only edits to an existing test are the import specifier, and the construction of an
   object that is now native.
2. Goldens are never regenerated in a lane. Rectangle fixtures, paint-list bytes, recorded traces and `expected.toml` come
   from NpOracle or from the owner's reference. A mismatch means the native code is wrong. `UPDATE_SPEC=1` may only turn
   `fails` into `runs`.
3. Deleting a test needs a named replacement in the lane's commit message.
4. Every TypeScript acceptance test has a Python twin, and a Rust twin where the SDK has the API.
5. A threshold (`boot_cost`, `budgets`, `frame_cost`) is not changed.

## 7. Risks and decisions the owner may overrule

### 7.1 The three biggest risks

1. **The object protocol is the one bet every lane stands on.** If its cost or its shape is wrong, all of waves C and D
   inherit the flaw. It also decides whether new classes really need no ABI edit. Mitigation: NpObjectAbiA builds a real
   slice first and measures it; B1.1 is the planned escape for a missed field. The fallback is the style the std table has
   today, one typed function per verb, which costs `abi.lock` churn but not correctness.
2. **Parity with an oracle that disappears.** The TypeScript library is the only specification of the UI, frame, menu and
   style behaviour, down to paint-list bytes and the order of listener calls. NpOracle records it.

    The 51 `gnoblin-js` tests meet the native code together only at NpFlip, and a flip with many red tests would stall the
    critical path. Mitigations:

    - Python twins and fixtures in every lane, and the seams of 6.2.
    - A rehearsal branch that rebases the flip onto the tip every few days in wave D, so the failure list is known before
      NpFlip starts.

3. **The two biggest rewrites sit on the critical path with thin evidence.** Moving the JavaScript runtime onto node functions
   (removing the engine mirror) and porting the input matcher are both estimated from line counts. The matcher is about 3.5k
   lines with tiers, scopes, click versus drag and cancel on close.

    The closure drag path was already seen not to reach TypeScript in one rig (section 34). The Python loader port is not
    prototyped. If any of these doubles, the schedule moves by weeks.

Smaller risks, each with an owner lane:

- **Build time.** A generator in several `build.rs` files adds work to every build, and every `gnoblin-js` test binary
  already links the core (170 MB in a debug build). NpGenOut measures it.
- **Fine-grained calls.** Vector math, property reads inside a `compute` closure and per-repaint `paint` overrides cross the
  ABI many times a frame. Mitigation: batch functions in the catalog (`compose_many`), dirty flags, and native defaults.
- **Hot reload of native widgets** (decision O6).
- **Two request routers.** The native focus and request policy must not answer beside the TypeScript one. It is enabled at the
  flip only (NpStdPolicy).
- **`inert` drift.** Moving two hand-kept lists into the catalog changes how `inert_surface` reads its input.

### 7.2 Decisions

Each decision has a recommendation. The owner may overrule any of them.

| #   | Decision                                                                          | Recommendation                                            | If overruled                                                                           |
| --- | --------------------------------------------------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| O1  | The object model every shell needs lives in `gnoblin-core-impl`, one copy         | Yes. Python and Rust gain tiers and collections too       | A JS-only model in `gnoblin-js` Rust is 5 days cheaper and leaves Python and Rust thin |
| O2  | Generated JS and Python modules are embedded in the runtime libraries             | Yes. They cannot drift from the catalog hash              | Install under `share/gnoblin/{js,python}`, keep both env overrides                     |
| O3  | Only `gnoblin-core`, `gnoblin-std` and `gnoblin-std/xr` resolve                   | Yes, as D13 did for the old names                         | Generate an alias module per catalog module                                            |

| O5  | Style objects are native handles with generated accessors                         | Yes, with a `style.set(record)` form for bulk writes      | Keep a script-side proxy over a record, which brings a script layer back               |
| O6  | Native widgets belong to the generation and are rebuilt on reload                 | Yes, as today. State kept per widget id is a later option | Keyed retention with `state_put` and `state_get`                                       |
| O7  | The starter lives in `shells/default/`, not `examples/`                           | Yes. It ships as the default shell                        | `examples/00-default-shell`                                                            |

### 7.3 What this design did not verify

- No lane was built or run. Every estimate is from line counts and the import graph.
- The cost of the object protocol (4.2), the build-time cost of the generator (3.7), the PyO3 port of the Python loader (2.3)
  and the exact member lists of the catalog tables (4.4, which follow the TypeScript classes by the surface rule) are
  `[INFERENCE]`. The first two are measured by the first two lanes; the last is mechanical from NpOracle's declarations.
- The import-graph classification of 6.2 is by direct imports between files. A lane's own audit may move a module from one
  column to the other.
- Names such as `NpStdUi` are this file's. Lane agents may be given other names without changing anything above.
