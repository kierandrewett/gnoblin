# Constants audit: compositor group

Read-only audit of the constants in `gnoblin-compositor`, `gnoblin-wm`, `gnoblin-layers`, `gnoblin-render` and `gnoblin-parity`. No code was changed or built.

Questions per constant:

- **Q1** Would a user want it configurable?
- **Q2** Does an upstream source own the value? If so, how should it be obtained?
- **Q3** Is it needed at all?

## Method and limits

- Listed with `grep` for top-level `const` and `static` items, then checked by reading the files. Items inside `#[cfg(test)]` modules are excluded.
- `model_test.rs` in `gnoblin-render` is a test harness (4 items) and is excluded.
- `const fn` and `const` items inside function bodies are not listed. Inline magic numbers were spot-checked, not exhaustively enumerated. [INFERENCE] some inline literals remain unlisted.
- Config leaves were read from `crates/gnoblin-schema/schema/*.toml` and `design/rust-compositor.md` D1-D30.
- Upstream checks were fetched where the source was reachable. Items marked [INFERENCE] or "unverified" were not checked against the upstream source.

## 3. Top ten wins

Ranked by user value over effort. Items marked CONFIGURE add a leaf. Each leaf needs a schema entry in `crates/gnoblin-schema/schema` and a default equal to the current value.

1. **`window-management.pointer-rest-delay`** (pointer_focus.rs:20): CONFIGURE, int ms, default 200, range 0..2000. The bool already exists and the delay has no leaf. Risk low, effort S.
2. **`window-management.cascade-step`** (placement.rs:35): CONFIGURE, int px, default 32, range 4..256. Users with large windows want a different offset. Risk low, effort S.
3. **`window-management.default-size`** (wm.rs:85): CONFIGURE, two ints px, default 800x600. Apps that send no size land at a size the user picks. Risk low, effort S.
4. **`window-management.min-visible-strip`** (drag.rs:18): CONFIGURE, int px, default 75, range 16..work area. Only used with the strip constraint. Risk medium, effort S.
5. **`ipc/settings.rs:52` `UNSET_ACCENT` sentinel**: REMOVE, replace with `Option<f64>`. Type system instead of a magic `-1.0`. Risk low, effort S.

Also worth doing: `portal/ui.rs` deadline is caller-supplied, so no change is needed there. The `BTN_LEFT` value (ipc/portal.rs:351) can be derived from the kernel header, value verified at [input-event-codes.h](https://github.com/torvalds/linux/blob/master/include/uapi/linux/input-event-codes.h).

## 4. Constants to leave alone, and why

- IPC wire keys, error codes and event names (ipc/session.rs, ipc/settings.rs, ipc/server.rs, ipc/extension.rs, ipc/portal.rs, layout/error.rs): wire format. Changing one breaks clients.
- Permissions `0o700`, `0o600` (ipc/path.rs:39,42): security.
- Safety bounds: `MAX_FILE_BYTES`, `MAX_IMAGE_EDGE`, `MAX_PHYSICAL_SIZE`, `MAX_FRAMES`, `MAX_PASSES`, `MAX_UNIFORMS`, `MAX_BLUR_RADIUS`, `MAX_BLUR_PASSES`, `MAX_INHERIT_DEPTH`, `MAX_THEMES`, `MAX_SCAN_STEPS`, `MAX_CASCADE_STEPS`. Renderer and parser limits. Raising them is a risk, not a preference.
- Numerical and mathematical constants: `SINGULAR_RATIO`, `BOUND`, `C1`, `C3`, identity matrices, colour constants.
- Layer grammar: `GNOBLIN_NAMESPACE`, `MAX_LOCAL_LEN`, `MAX_EXTENSION_ID_LEN`, `Band::ALL`. Part of D28.
- Parity test harness (all 9 items): test tooling only.

## 5. Needs Kieran

- Portal queue bounds (`MAX_QUEUED`, `MAX_QUEUED_PER_APP`, `MAX_PER_APP_PER_WINDOW`, `RATE_WINDOW_MS`, portal/queue.rs:15-21): these are anti-abuse limits. Should any become a user leaf, or stay fixed?
- Layer registry `DEFAULT_LIMIT` (registry.rs:47): fixed guard, or a config leaf under the provider's config?
- Which leaves are user-facing and which are Bingux shell settings? `default-size`, `cascade-step` and `pointer-rest-delay` could live in the core config or in the shell.
- `CursorSource::DEFAULT_ORDER` (cursor/mod.rs:120): D20 changes the default chain. Keep the constant as the fallback, or move the default to the schema alone?
