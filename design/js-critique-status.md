# Status of the open items of the JavaScript shell critique

The critique (`design/js-research/fable-critique.md`, written at `4a968d202`) traced its claims in code and reproduced none.
This page says, for each security or correctness item still open when this lane began, whether it is **confirmed**,
**refuted** or **fixed** on the current tip, with the evidence and the test. A test name is the proof; where a claim has no
test it says so. Measurements are a debug build on one 4-CPU Agent37 box, one run.

## The write-loss class, staging and the frame's order

Critique plan items 1, 9 and 12, each checked against the tip before anything was changed. Red means the test failed on the
tip (`a890416fa`) with the tests of this lane added and nothing else.

**Item 1, writes lost on refusal.** The critique's claims about text calls, `failed_op` -1, exhausted resends and the lock
check's hang were already fixed on the tip (`ca31fd1e0`, `641dfca50`, `5b464c66b`), and the tests the plan asks for were there: `an_output_apply_refused_stale_base_is_sent_again_and_its_answer_reaches_the_application`
(an `Output.apply` answered after a stale), `a_refusal_with_no_op_index_sends_the_whole_frame_again_on_the_new_base` and
`a_placement_dropped_after_its_resends_is_laid_out_again` (placements converge after a `-1` refusal and after the resends
run out), `a_password_check_a_stale_refusal_dropped_is_answered_and_the_screen_takes_another_try` (a lock check after a
stale gets an answer), all in `crates/gnoblin-js/tests/write_refusals.rs`, all green on the tip. Whether a call is kept for a
resend comes from the schema's `secret` flag (`gnoblin_proto::tree_call_is_secret`); `PLAIN_TEXT_CALLS` is gone.

Two claims were open and are closed. **A secret call shared a transaction with the frame's other writes**, so a `stale-base`
that the frame's window writes caused lost the password check. The check now goes first and alone, and the rest of the frame
goes behind it (`split_secret` in `shell/txgate.rs`). Red: `a_password_check_goes_in_a_transaction_of_its_own_and_the_frames_other_writes_follow_it`
and `a_stale_refusal_of_the_writes_beside_a_password_check_does_not_cost_the_check`.

**The layout driver does not compare the mirror with its last placement, and does not need to.** The critique's loss was
permanent because nothing laid a lost placement out again; the shell now hands every write it gives up on back to the layout
(`lost_writes`, `relayLostWrites`), and a refusal that names no op sends the whole frame again, so no way of losing a
placement that the traced chain describes is left. A level-triggered comparison would also run against a mirror that is
right to differ: a client that sets its own size, a value the compositor clamps, and a write refused for a reason no base
cures (`read-only`, `too-large`) would be written again every frame and refused again every frame. The shell forgets such a
write on purpose (`give_up_refused`). If a loss turns up that this chain does not cover, the test that reproduces it comes
first.

**Item 9, staging shared its side effects.** Confirmed by a red run: of `stage_effects.rs`, 5 of 6 tests failed (a stage that
spawned and then threw left the program running; a reload started a second copy; a refused reload doubled the running
config's program; a reload that dropped a spawn left its program; a reload that changed it left both). A staged generation
now holds its `gnoblin.spawn` calls back and starts them when it takes over; a spawn of the same command and options as a
process the running config started takes that process over (same `id`, same `pid`); a process the new file no longer
starts receives SIGTERM; a process a handler started is left alone. Each process has an owner, the generation that started
or took it over (`Processes::owner` of `gnoblin-shell-host`). The canvases, measurements, XR nodes, output applies and lock checks a failed stage
made are given back with the pending writes (`HostState::begin_stage` and `abandon_stage`, `bindings/stage.rs`). Not
covered: a session verb (`gnoblin.session.lock()` and the like) called at the top level of a file runs at once, stage or not.
A `Process` made at the top level has `pid` 0 until the generation has taken over, which is the one visible change.

**Item 12, the frame's order lived in comments.** `shell/frame.rs` holds the frame as `STAGES`, one entry per stage with the
comment that says what it needs from the stages before it, and `tests/frame_order.rs` records every call a frame makes into
the entry and pins the order. The test passes on the tip and after the change, as a pin should; its failing case is a
mutation (two stages swapped in the table), run once and not kept.

**The lock leftovers** were closed before this lane: the J8 decision is recorded in `design/js-runtime.md` (J8, "Recorded
exception") with its trade-off, and `docs/session-lock.md` says what the lock protects; every pending check has a deadline
(30 s, `CHECK_DEADLINE`; `a_check_the_compositor_never_answers_fails_once_its_deadline_has_passed_and_the_screen_takes_another`);
and the lock is held by a lease, not a flag (the row above, `5b464c66b`, with the card taking over on a lapse in
`crates/gnoblin-compositor/tests/lock_card.rs`). Nothing there changed in this lane.

## Inert settings and properties, and what was decided

Tree properties no native code reads, each with its reason in the test: `effect.algorithm` (one blur kernel, said in the
schema), `node.parent` (the structure carries it), `node.tags` (selector keys of the retired Lua API), `screen.screen_x`,
`screen_y`, `screen_width`, `screen_height`
(declared read-only, never published, so a read is 0) and `workspace.index` (the compositor creates no workspace node, so
the class, its `active`, `output` and `activate`, and `window.workspace` are unused). Decision: marked, not removed; each
should go with the next schema change, because the generated declarations still offer them.

The library says "not applied" for `OutputProfile.vrr`, `Camera2D` transforms, `Camera3D`, `Viewport.clearColor` and the style
properties no effect kind draws (`background`, `filter`, inset shadows); `docs/shell-api/outputs.md` and `docs/js-style.md`
now say "Not applied yet" for each. The mouse and touchpad settings are accepted and not applied until the libinput applier
lands (`gnoblin-v09s`, the InputSettings lane); this lane did not touch them. Configuration settings nothing reads are the
`unused` rows of `design/config-reload.md`, held to the code by `crates/gnoblin-config/tests/apply.rs`.

## Found on the way, and closed

- **A window that arrives under the lock defeated the card (fixed).** Root cause, read from a timeline of the compositor's
  lock path on the unmodified test: the shell never spun. The window mapped, and 13 ms later the stock focus policy
  (`FocusPolicy.onAdded`) wrote the seat's focus onto it; from then on `shell_lock_key_target()` was `None` and every key
  was dropped, while the shell, healthy, renewed its lease every 500 ms, so the compositor judged the lock screen held and
  never drew the card (`lock_card.rs`, `lock_ui_held`). Nothing blocked or waited: the lease said the screen was alive and
  said nothing about the keyboard. The lock screen now counts as held only while the keyboard is on its entry, so the card
  takes the keys one second after it is not; the screen takes the keyboard back on its next frame; and a focus the shell
  writes under a lock moves no keyboard and leaves the window that had the focus alone. Red before, green after:
  `a_window_that_arrives_under_the_lock_does_not_leave_the_session_with_nobody_to_type_a_password_to`, the five-window,
  closed-window and healthy-shell-thief variants (`js_lock_failures.rs`) and
  `a_shell_that_renews_its_lease_but_has_lost_the_keyboard_loses_the_lock_ui_to_the_card` (`lock_card.rs`). Windows that
  map before the lock, while it is taken, never draw, never commit, or arrive and go during a spin do not break it
  (`a_client_that_never_commits_does_not_take_the_keys_from_the_lock_screen`,
  `the_stock_focus_policy_racing_wrong_passwords_never_unlocks_and_leaves_somebody_to_type_to`); a shell that crashes with
  a window open under the lock leaves the card to take the password at once
  (`a_shell_that_crashes_with_a_window_open_under_the_lock_leaves_the_card_to_take_the_password_at_once`).
- **The spin tests of the previous lane never spun (fixed).** Their script began `Object.assign(globalThis, { gnoblin,
... })`, and `gnoblin` is a read-only global, so `init.ts` threw at line 2, no hook was registered, and the shell's own
  screen took the right password inside the bound. Each spin test now reads from outside how long the shell's thread has
  been inside one tick (`Shell::stuck_for`) and fails unless the shell was still in the spin when the card took the
  password; they spin for real (4.4 to 4.7 s to the card, the shell inside one tick for as long).
- **Keyboard focus after an unlock (fixed, both ways).** The shell wrote the seat's focus onto its entry and the
  compositor, taking that for the window focus, forgot the window that had it. A write onto a shell node under a lock no
  longer clears `focus`. `js_lock_boundary.rs` asserts the window hears a key after the unlock through the shell's screen and
  through the card, and, with a window that arrived under the lock, that the window that had the keyboard keeps it
  (`a_window_that_arrived_under_the_lock_leaves_the_keyboard_with_the_one_that_had_it_after_an_unlock_through_the_shells_screen`,
  `..._through_the_card`) and that a lone window that arrived under the lock gets it
  (`a_window_that_arrived_under_the_lock_has_the_keyboard_after_the_unlock_when_no_window_had_it_before`).
- **A shell started under a lock** takes no focus to give back from the shell's side; the compositor's own record serves it,
  the same fix.

Bounds, measured in a release build on a 4-CPU box, 20 runs each (`js_lock_bound.rs`, from the instant of the event to the
password accepted): 3.313 / 3.357 / 3.404 s (min / median / max) after the last healthy beat, against the page's 3 s plus
half a second; 1.189 / 1.255 / 1.306 s after the keyboard left the screen, against 1 s plus half a second. This replaces
an earlier claim of 100 ms for the session loop and 50 ms for the card's pump, which the first debug run (3.51 s) refuted:
the lapse and the grace are each noticed on a loop turn, and the check's answer is applied on one.

## What is not proven

No test reads pixels; the check is a scripted double, not PAM; a real runtime process is killed and frozen but nothing types
at it, so the card taking a password after a kill is proved in-process; the bounds were measured on an idle machine, with
the shell driven by the test, and the card's first frame is not timed.
