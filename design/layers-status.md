# Layers: status and gaps

> **The `gnoblin-wm` crate is deleted** (lane W6, `design/cutover-survey.md` sections 13 to 15). Every `gnoblin-wm` name and `crates/gnoblin-wm/...` path below describes the code as it was when this document was written. Window state is now the compositor's own record (`crates/gnoblin-wayland/src/fallback.rs`), and placement, focus, rules, workspaces and layouts are the stock Lua shell's (`data/lua/gnoblin/shell/`).

> **The layer registry and the window frame protocol are deleted** (lanes 8B and 8C, `design/cutover-survey.md` 16.1). `crates/gnoblin-layers`, the `layers.register` IPC verb, `schema/layers.toml`, the layer records in `State`, the `layers` configuration section and `gnoblin_window_frame_v1` no longer exist; the file and line citations below describe the code as it was. Layer-shell reserved zones never used the registry and are unchanged.

## Outcome (after lanes 8B and 8C)

The registry design in `design/layers.md` is retired and nothing replaces it: the owner kept layer-shell surfaces protocol-owned (O14 b, `design/cutover-survey.md` 16.6). What a layer surface is, is `zwlr_layer_shell_v1.rs` alone. It places the surface, adds its zone to the output's reserved insets, grants exclusive keyboard on the top and overlay layers, and tracks its popups. Six tests in `crates/gnoblin-wayland/tests/layer_shell.rs` pin that, and they pass on the tree before the registry went and on the tree after it.

Two parts of the design were never built and leave step 8 with it: the `gnoblin.alerts` layer and the `gnoblin.window_menu` extension. The compositor side of the menu is built and tested (`window.request_menu` and the `menu_requested` signal), and `unresponsive` stays the property and reason for the alert. What is missing is a stock shell node that draws either, which is a new shell feature and not part of the cutover. Step 8's green line is "portal tests; the `portal.ui` replacement path" (`design/archive/node-api-refactor.md`, step 8 row).

The rest of this file is the record of what the design asked for and where the code stood at `6ce209796`. Its status cells and the outcome in brackets after each gap and slice are brought up to date; its evidence cells and citations describe the code as it was.

## Answer: do window frames use layers?

No. The window frame path bypasses the layer model.

- `crates/gnoblin-wayland/src/protocols/gnoblin_window_frame_v1.rs` never calls the registry. The file has no `register`, `LayerRegistry`, `gnoblin_layers` or `LayerProvider` reference.
- Ordering and hit testing use the old structures. `frame_window_at` (`:640`) walks `self.wm.stack()` and looks up `self.frame_tables.frames` (`:644-649`). The layer registry is not consulted.
- Frames are not painted at all. `frame_surface_committed` (`:790`) stores the committed regions and presented flag. Those are read only by the `window_frame()` snapshot (`:516`) and by `frame_window_at`. No code draws the frame surface. `crates/gnoblin-backend/src/render/compose.rs` and `crates/gnoblin-render-frame` never reference the window-frame protocol or `frame_tables`. The header comment at `gnoblin_window_frame_v1.rs:76-80` says the frame is configured with zero extents and is not composed yet.
- Only the window's own surface is drawn. `State::sync_content` (`state.rs:1857`) calls `composer.set_window_content` (`state.rs:1862`) for the window's content, not for its frame.
- `gnoblin.window_frame` does not exist as a layer: no `register_layer` call names it (`grep -rn "window_frame" crates --include=*.rs` returns the protocol, its tests and `state.rs` lifecycle hooks only). `design/layers.md:204-215` describes it as a layer with paint and input areas. Neither exists today.

What the lifecycle hooks do: `refresh_window_frame` (`:671`, called from `state.rs:1847`) creates or refreshes the entry (insert at `:774`); `close_window_frame` (`:778`, called from `state.rs:1758`) removes it; `frame_pointer` (`:533`, called from `state.rs:1572`, `:3265`, `:3280`) routes pointer input to the frame's regions.

Suspected bug (needs a test, not yet written): `frame_window_at` uses `?` at `:649` on the frame table lookup. Any visible stacked window with no frame entry returns `None` for the whole search. Most windows have no frame, so a frameless window above a framed window hides the framed window's titlebar outside the top window. Expected: the search continues past a window with no frame. Test to add: `a_frameless_window_above_a_framed_window_does_not_hide_its_frame`, beside `a_pointer_over_overlapping_windows_reaches_the_topmost_frame` (`crates/gnoblin-wayland/tests/window_frame.rs:551`).

Existing frame tests (all in `crates/gnoblin-wayland/tests/window_frame.rs`): `a_mapped_window_is_offered_a_frame_and_presents_it` (`:289`), `a_buffer_of_the_wrong_size_is_a_protocol_error` (`:401`), `a_pointer_over_overlapping_windows_reaches_the_topmost_frame` (`:551`), `a_pointer_over_a_tiled_window_reaches_its_own_frame` (`:610`), a renderer-crash test (`:667`), and a closed-window test (`:690`). None of them checks a painted pixel, because nothing paints the frame.

## Ranked gaps (user impact first)

1. **Window frames are never drawn.** `compose.rs` and the backend do not reference frame surfaces. A frame-drawing client (the only way to get a frame today) is hit-tested but invisible. Largest user-visible gap. [Gone: the frame protocol is deleted, lane 8B.]
2. **Frame hit testing hides framed windows** (`gnoblin_window_frame_v1.rs:649`, `?`). Pointer over a frame can go to the wrong window whenever any frameless window is above it. [Gone with the frame protocol, lane 8B.]
3. **Frames are not layers.** No `gnoblin.window_frame` record, no registry ordering, no input areas from the registry. Blocks the design's paint/input split (`layers.md:204-215`). [Withdrawn: no frame and no registry.]
4. **Popups have no defined draw path in the compositor.** `compose` draws only the root `set_window_content` (`state.rs:1862`). Popups go through `xdg_shell.rs:176` `popup_committed` and `wl_compositor.rs:94-95`, and nothing shows them drawn above their root in compose. [INFERENCE: not traced end to end; test needed: a menu popup above its parent is visible in a capture.] [Not registry work; not re-checked.]
5. **Modal input policies `Passive` and `Grab` are refused** (`state.rs:2484-2489`). Any portal or dialog asking for them is dropped with a warning. [Gone: `InputPolicy` is deleted, lane 8C. A grab would be a seat feature, `Seat:grab`, which does not exist.]
6. **Capture secure masking parity.** Headless and nested route through `capture_redacted`. The x11 backend has no secure path found. No DRM backend exists in this tree, so the design's DRM readback has nothing to cover [INFERENCE: confirm the design still means DRM]. [Not registry work; not re-checked.]
7. **`layers.list` IPC is absent.** Only `register` exists (`layers.toml:22-23`). The parity test and clients cannot read records. Design says `layers.list` is the one list for everything. [Withdrawn: there is no registry to list. The parity scenario `layer-surface-stacking` is kept as a refused expectation.]
8. **`parent_window` for `wayland:` handles** is only half wired. Lookup exists (`ipc/server.rs:900`); portal consumption is untraced [INFERENCE]. [Not registry work; not re-checked.]
9. **`window_menu` is not a shipped extension.** The core request path exists (`state.rs:2324`) but nothing draws a menu for it. [Dropped from step 8: a stock menu is a new shell feature.]
10. **`gnoblin.alerts` absent.** Design phase 8. [Dropped from step 8: a stock alert is a new shell feature.]
11. **Lua `gnoblin.layers` absent** (phase 10). Blocked on D22. Phase 9's config `layers` section is also missing. [Withdrawn: the config key is refused with a migration sentence and the Lua API will not be built.]

## Phased plan (lane-sized, tests first)

Each slice writes its failure-mode test first, then the code, and pushes green on its own. Gates per the lane rules (`check`, `clippy -D warnings`, `fmt`, `test` for touched crates, `xtask dupes/logging/deps/layout/docs-parity`).

Accept: the pointer over the framed window's titlebar outside the top window reaches its frame. [Withdrawn with the frame protocol, lane 8B.]
- **Slice B, register frames as layers.** Register `gnoblin.window_frame:<id>` as a window-scope entry above its target with `Wm::register_layer`, following the design's built-in rule. - **Slice C, draw frames.** Compose the frame surface above the window content in `compose.rs`, ordered by the frame list. - **Slice D, frame input areas.** Move pointer lookup for frames from `frame_tables` to the registry input areas, so CSD drag areas still move the window (`layers.md:544`). Test: drag over a CSD titlebar moves the window while the frame paints over it. [Withdrawn with the frame protocol, lane 8B.]
