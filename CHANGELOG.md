# Changelog

## Unreleased

### Added

- The JavaScript shell's session, process, timer and event API (lane JsHostApiA; design/js-runtime.md, "Host API A status"; `docs/js-host-api.md`). `gnoblin.session` (`status`, `logout`, `poweroff`, `reboot`, `suspend`, `hibernate`, `lock`) returns typed `Operation`s, `gnoblin.runtime.reloadConfig()`, `gnoblin.process.spawn/list/byId` with `ProcessListener.onExit`, `gnoblin.timers.after/now`, `gnoblin.on/once/off` for every schema signal, `gnoblin.find`, `gnoblin.focus.history` and `gnoblin.version()`. `gnoblin.spawn` now returns the `Process`. `requestTransition` is removed from the declarations: it was never implemented.
- Outputs and desks in the JavaScript shell (lane JsOutputs; design/js-runtime.md, "Outputs status"; `docs/js-outputs.md`). `gnoblin.outputs` is a live collection of `Output` objects (`name`, `make`, `model`, `mode`, `scale`, `x`, `y`, `width`, `height`, `primary`, `enabled`, `area`, `workspace`, `show`) with `OutputListener` (`onConnected`, `onDisconnected`, `onModeChanged`, `onScaleChanged`, `onGeometryChanged`); each output shows its own workspace, a layout computes in the area of the output that shows its workspace, `Bar` takes an `output`, and workspace sets show each entry on its own output. The windows of an unplugged output move to the workspace a remaining output shows, fitted to it, or wait hidden (focus dropped) for the next output; `Client.moveToWorkspace` and `Client.moveToOutput` refit, hand the focus on and refuse a fullscreen window and a dialog; a dialog (`Client.parentWindow`) is centred in its parent, moves with it and follows it across outputs; `Client.fromLauncher` feeds `focus.newWindows`. The tree `window` class gains `parent_window` and `from_launcher` and the `screen` class `output_scale`, and the compositor publishes them with each screen's `make`, `model`, `mode` and `primary`. The headless backend takes an output at run time through `SessionConfig::output_tap`. `Output.apply` is not available: the compositor runs no call on a screen node.
- The JavaScript shell answers a client's requests of its window (lane JsClientRequests; design/js-runtime.md, "Client requests status"; docs/typescript-shell.md, "Window requests"). `data/js/gnoblin/window_state.ts` answers `maximize unmaximize fullscreen unfullscreen minimize unminimize close raise lower activate move resize` as `Window:on_request` did in the Lua shell, with the same expected values (`crates/gnoblin-js/tests/client_requests.rs`: the 12 cases of `states_test.lua` and the `shell_test.lua` raise, activation and repeat-fullscreen cases) and three tests with a real Wayland client (`crates/gnoblin/tests/js_shell.rs`). `ClientListener.onRequest(client, request)` hears every request first; the first listener to call `request.handle()` answers it and the built-in answer does not run; `windowState` exposes the stock answers. A fullscreen window covers the whole output (the bars give way, `barsGiveWayTo`) and keeps the rectangle it had; a minimise hands the keyboard focus to the topmost window left; `Client.raise()` keeps a fullscreen sibling on top; a `move` or `resize` request starts the stock pointer drag for a floating window. Changed: window rules merge every matching rule in list order (the later wins per field) as the Lua rules did, `first: true` replaces `all: true`, and `reapply` is on by default and also follows focus; the stock config declares four workspaces, `1` to `4` (`WorkspaceConfig.name` is new), as the Lua stock config did, and the starter `gnoblinctl config init` writes matches.
- The XR program publishes controllers (lane XrControllers; design/js-xr.md, docs/xr.md "Controller nodes"). New tree class `controller` (`crates/gnoblin-schema/schema/tree/controller.toml`): the aim pose in `x y z rotation` (the room's node units, y up), `hand`, `tracked`, `trigger`, `grip`, `thumbstick_x`, `thumbstick_y`, `thumbstick_click`, `primary`, `secondary`, and a shell-written `claimed` list. An observer may make controllers and write their values (not `claimed`), with its own rate allowance apart from the head's, and they are destroyed with its connection. `gnoblin-xr` reads both hands through OpenXR actions with a subaction path for each hand, writes one node for each hand at most once a frame, destroys it when the hand is lost, and withholds a claimed trigger, grip or thumbstick from the window under the ray. `Runtime::locate_controller` is replaced by `Runtime::locate_hands`. No headset was used.
- The JavaScript shell's window style (lane JsStyle; design/js-runtime.md, "P8a style status"; `docs/js-style.md`). `gnoblin.clients.style`, a workspace's `clients.style`, `clients.where({ ... }, { priority }).style` and `client.style` are style scopes with `ClientStyle`, `Border`, `Shadow` and the filter classes as ordinary ES classes; a client takes each property from the highest scope that sets it (defaults, global, workspace, selections by priority then order, client), `unset` reveals the inherited value, `null` and `[]` are values, writing an element of an inherited list copies the list into the writer's scope, and an invalid value is refused with its property path (`Client#42.style.borders[2].width: must be finite and >= 0`). `client.computedStyle` is a frozen snapshot with the origin of each value and `client.styleWarnings` carries what is not drawn. A resolved style becomes the window node's `opacity` and `effects` (outer shadows and one backdrop blur); `cornerRadius`, `borders`, `background`, `filter` and inset shadows have no effect kind in the tree, stay in `computedStyle` and are reported once per reload as `not applied: style.<property>: <reason>`. `defineConfig({ style })` is applied as the global scope and `rules[].style` as the matched client's own style (`RuleEngine.styleOf` is gone); a reload without the lines takes the effects and opacity off the windows. The shell reads and writes the window `effects` and reads `skipped`.
- XR on the JavaScript shell (lane JsXr; design/js-xr.md, design/js-runtime.md "P9 XR status"; docs/xr.md "Scripting XR in TypeScript"). `gnoblin.extensions.xr` is null until the XR program has a session (the seat named `xr`) and an `XRExtension` while it has; `gnoblin/extensions/xr` exports `XRCamera3D`, `XRViewport`, `XRRoom`, `SpatialLayout`, `ViewMoveBinding` and `ViewResizeBinding` and fails at load, with a message, unless the session declared XR (`GNOBLIN_XR=1`) or the program has a session. The stock shell builds the room when the seat arrives, as `xr.lua` did (`arrangeRing` keeps the Lua golden numbers), a panel for each client except dialogs and secure clients, and takes it down with the seat. New `Node`, `Camera3D` and `View` classes make tree nodes (`crates/gnoblin-js/src/xr.rs`, `data/js/gnoblin/scene.ts`); a `View` shows a client without reparenting it. `ViewMoveBinding` (6-DoF grab, or by ray) writes only the View, and `ViewResizeBinding` writes the View's scale while the hand moves and asks the client for one new size on release, if the aspect or density needs it. The bindings read `controller` nodes that the XR program does not write yet (design/js-xr.md, "New native work"), so no drag starts on a headset. Tests: `crates/gnoblin-js/tests/xr.rs` over a fake tree, and one against a real compositor in `crates/gnoblin/tests/js_shell.rs`. No headset was used.
- The JavaScript shell's window menu, not-responding alert, launcher entry and the toolkit widgets they need (lane JsStockShellUi; design/js-runtime.md, "Stock shell UI status"; `docs/js-ui.md`). `Entry` (caret, selection, `onKey` events, `EntryModel` for the editing), `Clock` and `Bar` (a bar takes its room from the windows), `toast`, `overview` and a key event for canvases that hold the keyboard focus. The window menu (`menus.ts`) answers the compositor's `menu` requests, with the Lua menu's entries, keyboard navigation and submenu; the not-responding alert (`alerts.ts`) offers Wait and Force quit (`Client.kill()`); `Super+space` opens an `Entry` launcher when no `launcher` command is configured. `defineConfig({ menus: false })` and `defineConfig({ alerts: false })` turn the first two off. The titlebar now lies above the client instead of over its top (`client.bounds` is the content, `client.frameInset` the bar), obeys the seat's `double_click`, `middle_click` and `right_click` and fades the window out on close; layouts place frames. `Client` gains `unresponsive`, `kill()` and `lower()`.
- The rest of the `defineConfig` surface and a first-run experience for the TypeScript shell (lane JsConfigLists; design/js-runtime.md, "Lists, maps and the first run"; docs/typescript-shell.md, docs/typescript-config.md). New keys `autostart` (commands started once per session by the shell, tracked by argv, never started again by a reload), `protocols` and `touchpadGestures` (document sections, the second a whole list, added, changed and removed by reload like the others); `shortcuts` and `keybindings` are not keys, `keys` is the one way to bind a key. `gnoblinctl config init [DIR] [--force]` writes a short commented `init.ts` (`data/js/starter/init.ts`, as written the stock config) and the editor files, refuses to overwrite, and prints the next steps. A wrong key name fails the load with the nearest valid key within two edits and the valid ones; a table or list key of the wrong type names `config.<key>`, what it should be and what it was. `gnoblin-stock.d.ts` gains `decorations`, `autostart`, `protocols`, `touchpadGestures` and the array form of `spawn`. docs/typescript-shell.md is now the getting-started page and docs/typescript-config.md the reference for every key.
- A live console for the JavaScript shell (lane JsConsole; design/js-runtime.md, "P8 console status"; `docs/js-console.md`). `gnoblinctl console` is a prompt into the running shell and `gnoblinctl console --eval EXPR` prints one value as JSON (exit 0 or 1). The shell serves `js.sock` beside the owner socket (mode 0600, the peer's uid checked with `SO_PEERCRED`, off with `GNOBLIN_JS_CONSOLE=0`) and evaluates each newline-delimited JSON request between frames in its own generation, with the `gnoblin` global of `init.ts`, under the call budget: a runaway expression is interrupted without a strike against the generation. Values render with cycles, native-backed objects (`Client#3 { appId, title, ... }`), collections (arrays of summaries) and functions handled, and a size cap with a `truncated` flag. `inspect.clients()`, `inspect.workspaces()`, `inspect.bindings()` (trigger, owner, precedence rank) and `inspect.config()` (the effective merged config) return plain data, and `gnoblin.clients.focused` is the focused client.
- Focus, window rules and edge snapping in the JavaScript shell (lane JsStockFocus; design/js-runtime.md, "Focus, rules and snapping status"). `data/js/gnoblin/focus.ts` ports `focus.lua`: click, `sloppy` (the seat's `hover`) and `follow-mouse` (`hover-strict`) focus, focus on a new window, raise on click, auto raise and focus on a pointer rest, with the decision as a pure function (`focusDecision`) and a `FocusPolicy` listener that `defineConfig` attaches to `gnoblin.clients`. `rules.ts` ports `rules.lua` as data: `defineConfig({ rules })` with a query over `appId` and `title` (a plain glob or a RegExp instead of a Lua pattern; the translation table is in `docs/config/window_rule.md`), `focused` and `onWorkspace`, and the actions `workspace`, `floating`, `size`, `position`, `style`, `fullscreen`, `maximised`, `secure` and `skipFocus`; the first matching rule wins unless it says `all: true`, `reapply: true` applies it again when the app id or title changes, and an error names the rule's index and the field. `snap.ts` ports `snap.lua`: `ClientMoveBinding({ snap })` tiles a window dropped on a screen edge when `edge_tiling` is on, and `ClientResizeBinding({ edges: "nearest" })` moves the side nearest the press. `defineConfig` takes `focus`, `edgeTiling` and `dragConstraint` over the seat's read-only values (`InputContext.settings`). The host reports the pointer's edges on windows to `ClientListener.onPointerEnter`, `onPointerMotion`, `onPointerLeave`, `onPointerPress` and `onPointerRelease`, and an app id change to `onAppIdChanged`; `Client` gains `raise()`, `opacity`, `secure`, `floating` and a writable `fullscreen`. The cases of the Lua focus, rules and snap tests run against the fake link (`crates/gnoblin-js/tests/stock_focus.rs`) and one real-compositor test places a window by rule.
- The rest of the stock JavaScript layouts, workspace sets, the workspace slide gesture and the Lua shell's keys (lane JsStockLayouts; design/js-runtime.md, "P4b status"; docs/typescript-shell.md). `DwindleLayout` (a split tree kept between computes, a new window splits the cell of the window that had focus), `KioskLayout`, `StripLayout` (columns scrolled to the focused one, `scrollTo`, `focusLeft`, `focusRight`) and `Carousel3dLayout` (with `ring`) place as the Lua `Dwindle`, `Kiosk`, `Strip` and `Carousel3d` do, ported from `tiling_test.lua` and `strip_test.lua` case for case; the workspace names are `dwindle`, `kiosk`, `strip` and `carousel-3d`. A `Placement` carries `visible`, `tiled`, `z`, `rotation` and `scale`, and `Client` gains `tiled`, `visible`, `opacity`, `z`, `rotation`, `scale` and `animate(values, { duration, easing })` (an animated write with the Lua `ease` curves); the layout driver writes them, hides the windows of a workspace that is not shown, and now recomputes the shown workspace when focus moves. `gnoblin.workspaces.show(ws, { duration, progress })` slides the windows between workspaces, `gnoblin.after(seconds, fn)` runs a function at the first frame past a time, and `gnoblin.workspaces.sets` (`defineSets`, `activateSet`, `WorkspaceSets`) ports `sets.lua`. `WorkspaceSlideBinding` is the three-finger `Swipe3` slide of `gestures.lua`. `defaultConfig` binds `Super+1` to `Super+9` by position, `Super+Left` and `Super+Right` (strip focus) and `Swipe3`, and the new `launcher` config key binds `Super+space` to a command run through `spawn`. Not ported: the in-shell launcher entry, reduced motion, the other gesture actions, per-output workspaces.
- The JavaScript shell commits config document settings, observes the compositor's dialogs, and runs `on` and `setup` (lane JsConfigSlots; design/js-runtime.md, "P6 config document and slots status"; `docs/typescript-shell.md`). `defineConfig` keys that are sections of the config document (`dialogs`, `appearance`, `cursor`, `windowManagement`, `input`, ...; camelCase in a config, kebab-case in the document) are laid over the document the compositor holds and committed whole through `config.current` and `config.commit`; a value the validator refuses fails the reload with the document key path (`defineConfig: dialogs.style.radius: ...`) and keeps the running generation, and a reload that drops a key puts it back to its default. `gnoblin.dialogs.addListener` takes a `DialogListener` with `onConsentRequest` and `onSecretRequest`; a request has `kind`, `appId`, `subject`, `deadline` and `decline(reason)`, nothing allows a request or reads a secret, and the shell claims `dialogs.observe` only while a listener is attached. `on` (`clientAdded`, `clientRemoved`, `titleChanged`, `focusChanged`) and `setup(gnoblin)` are applied. `JsRole::connect` opens the slot and configuration connections; `JsRole::over_link` takes them as `JsRoleLinks`. `style` and `outputs` are stored and not applied (they need native style objects).
- The JavaScript shell's UI toolkit (lane JsUi; design/js-runtime.md, "P7 UI toolkit status"; `docs/js-ui.md`). `Canvas`, `Box` (a row or column flexbox with `gap`, `padding` and `grow`), `Text` (sized by the compositor's `measure`, with an estimate until it answers, and `ellipsize`), `Icon` and `Grid` are ordinary TypeScript classes in `gnoblin` (`data/js/gnoblin/ui.ts`): a canvas's `draw()` returns paint ops that are encoded into the node's `content` in the bytes the Lua shell wrote, geometry and paint are written only when they change, and pointer events reach `onPress` and the other handlers with bubbling. `Titlebar` (title, minimise, maximise and close buttons, a drag area; every number and colour a field of `TitlebarStyle`) is a canvas under the window's node, and `defineConfig({ decorations: true })` (set by `defaultConfig`) gives every client one and removes it with the window. `Client` gains writable `maximised` and `minimised`. Proven against a fake link (`crates/gnoblin-js/tests/ui.rs`) and against the real compositor (`crates/gnoblin/tests/js_shell.rs`: a `Box` and a window's titlebar read back from the tree through an observer, one pixel read by drawing the stored list with the compositor's painter).
- The JavaScript shell's pointer drag bindings run against the real compositor (lane JsPointerDrags; design/js-runtime.md, "P3c status" and "Pointer chord claims"). The input module consumes the `pointer_chord` signal: `start`, `update`, `end` and `cancel` call a binding's `onStart`, `onUpdate`, `onEnd` and `onCancel` with an event that carries `x`, `y`, `dx`, `dy`, `button`, `modifiers`, the input `context`, the `client` under the press, `workArea` and `dragConstraint`, and a pointer claim no longer needs the seat's published `pointer_x` and `pointer_y`. `ClientMoveBinding` (Super+Button1) and `ClientResizeBinding` (Super+Button3) move and resize a real window end to end; a move respects the seat's `drag_constraint` (`work_area` or `minimum_strip`; `dragConstraintMode`, `clampAxis` and `constrainRect` are exported, ported from the Lua drag rules with the same cases), and a fullscreen or maximised window declines both. A throwing `onUpdate` cancels that drag alone and is reported once. Proved by `js_shell.rs` against a real session with input injected through its input tap.
- Pointer chord claims on the seat (lane PointerChordClaim; `design/js-runtime.md`, "Pointer chord claims"). `Seat.claim` takes a chord that ends in a pointer button, `<Super>Button1`, `<Super>Button3` or the bare back button `Button8`, and the owner hears the drag as the new `pointer_chord` signal `(phase, claim, x, y, dx, dy, button, modifiers, time)`: `start` at the press, `update` as the pointer moves (at most once per frame, with the latest place), `end` at the release and `cancel` when the session locks or the pointer is unplugged mid-drag. The press is withheld from clients and the shell's nodes, no client hears the pointer during the drag, and the release comes back as `end` even when the modifier was let go first. A shell that detaches, an `unclaim` or a replaced claim ends the drag silently and the button's release is withheld as its press was, so no client is left with a button it never saw. The chord grammar knows `Button1` to `Button9` (X11's numbers: 8 is back, 9 forward) and a bare `Button8` or `Button9` is a chord; `Button1` to `Button7` still need a modifier. Applied by `crates/gnoblin-wayland/src/pointer_chord.rs` (a capture per pointer and button) and delivered by the compositor and `gnoblin-tree-client` (`TreeIncoming::PointerChord`); `gnoblin-js` consumes it (the entry above) and `gnoblin-lua` drops it, since the Lua shell claims no pointer chord.
- `dialogs.style` (lane JsDialogs; design/js-research/popups-portals.md, "7.5 Status"): a new config section restyles the compositor's own consent and passphrase dialogs with `radius`, `accent`, `font.family`, `font.size`, `button-layout` (`start`, `end`, `stretch`, `stacked`) and `scale` (docs/config/configure/dialogs.md). `gnoblin_portal_ui::style` clamps every request so a dialog stays safe: text keeps a contrast ratio of 4.5, an accent that does not stand out from the dialog (below 3) is moved toward white or black with black or white text on it, buttons are at least 88 by 32 points and Deny is never smaller than Allow, font 12 to 32, scale 1 to 3 (lowered until the dialog fits its bounds), radius at most 24; the 500 ms arm delay, the requester line and the lock icon have no setting. A new `dialogs.observe` slot lets a shell see each consent and passphrase request the built-in dialog is about to draw, for 250 ms, and refuse it by answering `deny`; anything else it does, and its silence or departure, leaves the same request to the built-in dialog, and it never receives or gives a passphrase. The JavaScript side (`gnoblin.dialogs`, `DialogListener`) is not done yet.
- The JavaScript shell survives its process and a config with nothing in it (lane JsGuardian; design/js-runtime.md, "P6 role wiring"; docs/typescript-shell.md). With no `init.ts` (or one that fails to load at startup) the shell runs the stock default config as a real runtime config: one floating `desktop` and the stock keys, claimed on the seat, instead of running bare (`JsShell::load_default_config`). `defineConfig` now layers over that config (`mergeConfig` in `gnoblin/config`): `workspaces` and `rules` replace as a whole, `keys` merge by canonical trigger (a stock key that shows a workspace the config dropped is removed), `gaps`, `style`, `outputs` and `on` merge by key, and the host binds the merged keys (`spawn`, `show`, `"close"`, functions), which `defineConfig` did not do before. `gnoblinctl config reload` reloads the JavaScript shell too: the runtime role's loop reloads the shell first (`ShellFrame::reload`, `ShellSlot::reload`), so a failing `init.ts` refuses the request with `config-rejected`, exit 1 and `file:line:column`, and the running generation stays; no new verb. `GNOBLIN_JS_WATCH=0` turns the config watcher off (`JsRoleConfig::watch`). Proven against a real compositor: the shell's owner connection closing and the runtime process being killed leave the compositor answering and the Rust fallback policy placing windows (a cascade) until the restarted shell reattaches and places every window again with the same ids (`crates/gnoblin/tests/js_shell.rs`, `js_guardian.rs`); the stock config and the layering run on the real tree; `config reload` is exercised through the real command line client against the shipped binary.
- `gnoblinctl check FILE` loads a `.ts`, `.mts`, `.js` or `.mjs` module graph through the `gnoblin-js` loader in a throwaway runtime with no compositor and a one second budget, and reports a syntax error, an unresolved import, a failing import cycle and a top-level throw as `file:line:column` in `.ts` coordinates (exit 0 ok, 1 problems, 2 usage); any other file is checked as `config validate` checks it. `--types` also runs an installed `tsc`, `tsc6` or `tsgo` (or `$GNOBLIN_TSC`) over the module with the generated `gnoblin.d.ts`, and says so on one line when none is installed. `gnoblinctl types init [DIR]` writes `gnoblin.d.ts` (refreshed) and `tsconfig.json` (only when absent) into the config directory. A module that cannot be found by the `gnoblin-js` resolver is now reported at the line of the `import` that names it (lane JsCheckCli; design/js-runtime.md, package P2).
- The JavaScript shell runs as the runtime role's shell (lane JsRole; design/js-runtime.md, "P6 role wiring"). `GNOBLIN_SHELL_VM=js` (or `js:<dir>` for a stock directory) starts `JsRole` in place of the Lua shell VM; unset, `0` and a directory are unchanged. `JsRole` connects `JsShell` to the owner socket through `SocketTreeLink`, loads `init.ts` (or `init.js`) from `$XDG_CONFIG_HOME/gnoblin`, runs one frame per loop turn, and owns a `ConfigWatcher`, a `JsReloader` and a `JsSupervisor`: a save stages a fresh generation against the live tree and `JsShell::swap_generation` makes it current with the same window ids; a syntax error or throw keeps the old generation and logs `file:line:column` once; a handler that runs past its budget is interrupted and the generation restarts, until three strikes in 30 s stop the restarts. `gnoblin-lua` gains `ShellFrame`, `ShellSlot::from_env_or_js` and `RoleRunner::run_with_js`, and the `gnoblin` binary links both shells (`xtask deps` lists `gnoblin-js` as a role entry crate for it). Proven against a real compositor in `crates/gnoblin/tests/js_shell.rs`. Running against the real tree fixed two binding bugs the fake compositor hid: node ids with bit 63 set (the compositor's own) are not exact script numbers, so they cross as stable `NodeHandles`, and a window the compositor has not parented is found by listing every node of the mirror (`TreeMirror::ids`) and not by walking from the root.
- New crate `gnoblin-js` (lane JsCore; design/js-runtime.md, package P1): the engine core of the JavaScript shell. `strip_types` turns a `.ts` module into JavaScript with a source map (oxc `=0.158.0`: enums, interfaces, `import type` and parameter properties; a syntax error carries path, line and column in `.ts` coordinates). `JsResolver` and `JsLoader` load `./x.ts` and `./x.js` (falling back to `./x.ts`) confined to a config root, rejecting a `..` that climbs out and a symlink that points out, plus host-embedded `gnoblin` and `gnoblin/<module>` sources. `JsGeneration` owns one QuickJS runtime and context with a wall-clock budget per call (an interrupt the script cannot catch), a memory limit, and errors remapped to the author's file, line and column. `JsHost::stage` builds and evaluates a fresh generation without touching the current one, and `JsHost::commit` swaps it in; a failed stage leaves the current generation callable. No tree binding and no Proxy yet. Tests: `cargo test -p gnoblin-js`.
- `gnoblin-js` hot reload (lane JsReloadSupervisor; design/js-runtime.md, package P5, engine side only): `ConfigWatcher` (`notify`/inotify, new workspace dependency, CC0-1.0) debounces an editor's save burst into one `ReloadRequest`, ignores `*~`, `*.swp` and `4913`, and watches the directories of every imported module (`JsGeneration::module_paths`). `JsReloader` stages the config, hands it to a caller-supplied commit closure and only then swaps; a syntax error, throw, runaway loop or rejected commit keeps the running generation and returns a `ReloadReport` with file, line and column in `.ts` coordinates. `reload_now()` is the manual trigger. `JsSupervisor` counts budget interrupts and panics on an injectable clock: three strikes in 30 s latch `Degraded`, keep the last good generation and stop restaging for a 5 minute cool-down. Process spawning, the Rust fallback and the compositor commit are not part of this change.
- The stock JavaScript library (lane JsStockLibrary; design/js-runtime.md, package P4): TypeScript under `data/js/gnoblin/` embedded in `gnoblin-js` as `stock_modules()`. `defineConfig` (closed key-action union `spawn`, `show`, `"close"`, function; `gaps`, `style`, `outputs`, `workspaces`, `keys`, `rules`, `on`, `setup`) with `desugarConfig` as the plan the host applies and `defaultConfig` (one floating `desktop`, `Super+1`, media keys); the `Layout` base class with `LayoutContext.gap`; `MasterStackLayout`, `GridLayout` and `MonocleLayout` match the Lua tiling goldens rectangle for rectangle and `FloatingLayout.place` matches all of `tests/shell/placement_cases.toml`; `Binding` and `BindingCollection` are declared without input wiring.
- `gnoblin-js` tree binding (lane JsTreeBinding; design/js-runtime.md, package P3): `JsShell` attaches to the compositor's tree, loads the embedded `gnoblin/host` module (`crates/gnoblin-js/js/gnoblin.ts`, re-exported by the stock `gnoblin` module), evaluates `init.ts`, announces `ready` for the snapshot's nodes parents first, and runs one frame at a time: it applies the compositor's batches, tells the script's listeners, and sends the script's writes as one transaction, with the one-in-flight and stale-retry rules of the Lua shell. A script sees `gnoblin.clients` and `gnoblin.workspaces` as live `Collection`s (`length`, `at`, `get`, `find`, `filter`, `map`, iteration, a data-only `where`, `addListener`) of `Client` and `Workspace` objects with stable identity; a client has `appId`, `title`, `focused`, `fullscreen`, writable `x`, `y`, `width`, `height` and `bounds`, `close()` and `focus()`, and after its window is destroyed `alive === false` and a write throws a `GnoblinError` naming `Client#3.x`. `ClientListener` and `CollectionListener` give each handler its origin object first; a collection listener is told of the existing members when it is added (replay on attach). A listener that throws is reported once per `.ts` site and never stops the others; each runs under its own wall-clock budget and a trip counts a strike. `gnoblin.spawn` goes to a host callback (`JsShell::set_spawner`). Tested against a fake compositor only; input events and layouts are not bound yet.
- `gnoblin-js` workspaces and the layout driver (lane JsWorkspaces; design/js-runtime.md, "P3b status"). A workspace is a script object: `new Workspace({ id, name, layout, gaps })` and the mutable `gnoblin.workspaces` (`add`, `remove`, `clear`, `show`); `workspace.clients` is a live, mutable collection of the same `Client` objects as `gnoblin.clients`, and `add` transfers a window between workspaces (a workspace or membership change never closes a window). A new window joins the first workspace flagged active (`initialWorkspace`, one function so the rule can change). ### Fixed

- Fixed, found by flaky tests: the `gnoblin-lua-sandbox` unit tests that expect the instruction budget to end an entry ran under the default 16 ms deadline, so a busy machine ended them on the wall clock first (`the handler deadline (16 ms) passed`): under eight busy loops on four cores 37 of 400 runs of the test binary failed, in ten different tests, among them `a_scoped_entry_that_runs_away_is_stopped_and_leaves_the_outer_entry_running` and `layout_profile_is_deterministic_across_states`. The guard now reads its deadline from a `Clock` (`Guard::with_clock`; `Guard::new` still reads the host's monotonic clock, so no host changes), and those tests run on a clock that never moves: 0 of 400 runs fail under the same load. The deadline has its own deterministic tests on a clock they move (`the_deadline_is_checked_on_every_hook_call`, `the_deadline_reads_only_the_guards_clock`, `the_limit_that_runs_out_first_ends_the_entry`, `a_rearmed_guard_gives_the_next_entry_a_fresh_deadline`, `a_scoped_entry_has_its_own_deadline_and_the_outer_entry_keeps_its_own`), and one test keeps the host clock honest. The two integration tests widen the deadline to an hour (`crates/gnoblin-lua-sandbox`).
- Fixed, found by a flaky `portal_e2e` test: the rig pressed a dialog's keys a fixed 150 ms plus the arm delay after the portal counted the offer. The offer and the keys reach the compositor on different sockets that nothing orders, and a key that finds no dialog is acknowledged and dropped, so an offer the compositor read late left its dialog open for ever (`Start did not answer within 30s`; reproduced on demand by holding the offer back 1.5 s, and 44 of 300 iterations failed when 3% of offers were held 0.9 to 2.5 s). The tap now writes a barrier behind each offer on the portal's own connection and the rig answers a dialog only after the compositor has answered it (`an_offer_that_reaches_the_compositor_late_is_still_answered`; 4 of 300 under the same amplifier, all inside a window of instance stalls). The compositor logs at debug level when a portal key reaches no open dialog, and when a portal request is admitted, offered to the `portal.ui` claimant or settled (`crates/gnoblin-compositor/src/ipc/portal.rs`). A failing wait now says how many dialogs were offered, held, settled and keyed.
- Fixed (`gnoblin-cyjm`): a window fades out when its client exits, or frees its buffer before its window. `shm::shape` and `shm::read_packed` refused a `wl_buffer` the client had destroyed (`is_alive`), so the composer could not read the last picture of a window whose client had disconnected or had destroyed its buffer before its toplevel, and the window was removed at once with no fade; only a client that destroyed the toplevel first faded. A destroyed `wl_shm` buffer is read like a live one: the compositor's handle keeps the pool mapped, and the protocol lets a compositor go on showing a destroyed buffer until its storage is reused (`crates/gnoblin-render-frame/src/shm.rs`). The same read now keeps a View of such a window, and the Vulkan renderer draws it, where both had dropped it. The tests run on a manual session clock and on every renderer the machine has (`crates/gnoblin-wayland/tests/render.rs`): `a_window_whose_buffer_is_destroyed_first_fades_out_over_the_whole_close_duration` and `a_window_whose_client_exits_fades_out_over_the_whole_close_duration` failed before (the first frame after the close showed no window), and `a_destroyed_window_fades_out_over_the_whole_close_duration` and `a_mapped_window_fades_in_over_the_open_duration` pin the paths that already worked, the second for the open animation whose frames the report found fully opaque from the first. ### Changed

- The grants frame is removed from the handshake, and the accept frame is now the whole preamble: the next frame is the client's first request. There is no IPC version bump. 0.2.0 is unreleased, so the wire stays at 0.2.0 and every client built before this change must be rebuilt, since one that reads a grants frame after the accept would misread the first reply. In-tree clients use `gnoblin_proto::IPC_VERSION` rather than a literal. Tests: `a_wrong_version_client_is_refused`, `a_client_sends_its_first_request_straight_after_the_accept`, `a_request_in_a_namespace_nobody_serves_is_refused` in `crates/gnoblin-compositor/tests/ipc.rs`.

- Window rules are the only writer of a window's `opacity` and `maximised`. A `maximised` rule maximises or restores the window through the same path as a maximise request, so the floating rectangle is kept. The carousel no longer writes window opacity, so a rule's opacity is not overwritten by an arrange. The tests are in `crates/gnoblin-lua/tests/lua/rules_test.lua` and `strip_test.lua`. The carousel's depth fade is dropped.
- Attaching the tree shell from a connection without the owner grant is refused `not-owner` (`failed_op` -1), not `not-privileged`. Test `attach_refuses_a_non_owner_peer` replaces `attach_refuses_an_unprivileged_peer`. A transaction from a connection that does not hold the tree is still refused `not-privileged`.

- The `gnoblin-xr` pointer's seat is named `xr`, not `gnoblin-xr-pointer`. The bridge reuses a seat named `xr` already in the owner snapshot and creates one only when none exists. Tests `pointer_creates_the_xr_seat_when_the_snapshot_has_none` and `pointer_reuses_an_existing_xr_seat` in `bridge.rs`.

- Frame callbacks reach a window that only a visible `View` shows, not only one on a monitor. A View shows the subtree under its `source` when the View and its ancestors are visible with non-zero opacity. A mapped window on neither a monitor nor such a View gets no frame callback; before, output-less mapped windows got them. Unit tests `a_visible_view_shows_its_source_subtree_and_a_hidden_one_shows_nothing` and the other `view` tests in `gnoblin-render` cover the visibility rules and a View inside its own source. Compositor-level callback tests are not added: there is no harness for the shell tree.

- The IPC trust boundary is the session owner's socket connection: a peer whose uid is the compositor's own (`SO_PEERCRED`, never the handshake). The owner-only members (`config.commit`, `config.reject`, `config.current`, `config.reload`, `portal.ui`, `portal.cancel`, `portal.key`, `capture.screen`, and offering a request slot) are refused `denied` to any other connection. The `runtime`, `services`, `portal` and `input` IPC roles are gone, so every program running as the owner's uid has the same IPC powers, including `config.commit`. Wayland `ClientRole`s are unchanged.

- The stock shell receives pointer edges on window nodes. While a shell holds the tree, a pointer that enters, moves over, leaves, presses or releases on a window sends the matching event to the window's node (a touch down sends a left press and release), as it already did for the shell's own nodes, and the window's client still gets the input. `Window:on_enter`, `on_motion`, `on_leave`, `on_press` and `on_release` in the stock shell therefore run on the real compositor, and focus follows them there. The workspace slide is covered by two tests in `crates/gnoblin-lua/tests/lua/shell_test.lua` (`showing a later workspace ...`, `showing an earlier workspace ...`): the new workspace is written one output width to the right or left and tweened to the origin, the old one is tweened out the other way.

- An X11 window is the same window node to the shell that a Wayland toplevel is. It is created as a `window` node when its surface commits its first buffer, with `title`, `app_id`, size and focus state published like any window's, announced ready once, and destroyed when the window unmaps or is destroyed. Until now an X11 window was managed but never had a node. The server pairs a window with its surface through `xwayland-shell-v1`, so a server older than Xwayland 23.1 (which names the surface by an object id Smithay does not let the compositor pair) still gets no node. Closing an X11 window now also ends its capture sessions, its renderer frame and its remembered keyboard layout, as a toplevel's close does. `gnoblin-backend` and `gnoblin-xwayland` no longer depend on `gnoblin-wm`: `gnoblin_backend::x11::Windows::handle` takes only the event and answers with `EventOutcome { window, changes, commands }`, where `changes` are `NodeChange::{Opened, Activate, Closed, Geometry, Title, AppId}` in place of the `gnoblin_wm::Effect`s, and `gnoblin-wayland` applies them to its window manager. `gnoblin-xwayland` also drops its `gnoblin-layers` edge, because the `surface_x11` layer record is registered by `gnoblin-wayland`. The composer's workspace slide takes `compose::SlideDirection`, a `gnoblin-backend` type, in place of `gnoblin_wm::WorkspaceDirection`. Tests in `crates/gnoblin-xwayland/src/windows.rs` (the table), `crates/gnoblin-wayland/src/xwayland.rs` (the changes against the window manager) and `an_x11_window_node_reaches_the_shell_like_a_wayland_window` in `crates/gnoblin-xwayland/tests/real_xwayland.rs` (skipped, with a printed reason, on a server older than 23.1).

- The XR extension's session crate (`extensions/gnoblin-xr/crates/xr-session`). `FrameLoop` drives a `Runtime` through the OpenXR session states: it begins the session once on `Ready`, ends it once on `Stopping`, runs one paired `wait_frame`, `begin_frame`, `locate_head` and `end_frame` per frame while the session is running, and stops cleanly on `Exiting`. - The owner's transaction can send an `input` op (`messages.toml`, `tree.op`): `node` is a window node, `seat` a seat node, `kind` one of `motion`, `button`, `scroll` or `leave`, with node-local `x` and `y`, `button` and `state` (0 release, 1 press) and `dx` and `dy`. - `gnoblin_render_software::render_view` draws a scene subtree through a `ViewCamera` into an image of the View's size. The camera has a pose (`position` and `rotation_degrees`) and a `ViewProjection`: orthographic, perspective with a vertical field of view, or an asymmetric frustum from four edge angles, which gives a stereo eye. Each node draws its buffer on its own plane, mapped to pixels through the camera, so a rotated node lands on its projected corners. Siblings paint in tree order, and invisible subtrees, zero-opacity subtrees and nodes behind the camera draw nothing. Opacity multiplies down the tree and blends straight alpha. Clipping ancestors cut their children to their bounds on their own plane. A non-finite transform or a camera that cannot project removes only the affected nodes, never panics, and the same scene always gives the same bytes. Node-api-refactor section 5 (render targets).

- A `View` node draws a scene subtree. The composer renders the source through the camera's projection, pose and `fov`/`near`/`far` (orthographic when `camera` is unset) into a cached snapshot, and draws it at the View's rect as a surface. The cache re-renders only when the source subtree or the camera changes, by generation counter. A source that contains its own View, or a missing node, draws nothing. The `Screen` class extends `View`, so its wire field numbers from `make` onward shift by one (`camera` is 19); the tree schema is 0.2.0 and unreleased.

On by default when the stock Lua library is installed at `<prefix>/share/gnoblin/lua/gnoblin`. `GNOBLIN_SHELL_VM=0` turns it off; any other non-empty value names the directory the VM loads instead. With no installed library and the variable unset, no shell VM is started and nothing is connected. When the VM runs, the role tries to start it and, on any failure, logs the cause by name and keeps serving with the slot empty. The VM opens its own session on the owner socket, found by the same rule as every other role (`GNOBLIN_IPC_SOCKET`, else `$XDG_RUNTIME_DIR/gnoblin/ipc.sock`), handshakes with it and attaches the tree on that connection; a refused or missing socket is named at connect time and the VM does not run. The role calls the VM's `tick` on every loop turn, not only when a change batch arrives, because the link is polled on each frame. Node-core step 3, slice 10 (part).
- The shell VM waits for its mirror. `boot_mirror` polls the link until the attach reply and the whole snapshot have arrived, so a shell that attaches before the compositor has sent its snapshot no longer boots with an empty tree. The loop is covered over the real socket wire (`tests/shell_loop.rs`): a compositor change batch sends no transaction, and a frame in which the VM wrote one sends exactly one `tree.transact`. Node-core step 3, slice 10 (part).

- The tree's frame boundary (`gnoblin-wayland`, `tree_frame.rs`). Each frame drains the transactions the shell queued through `TreeQueue`, in arrival order, before the composer draws, and applies each whole or not at all through `validate_and_apply` against the scene the composer draws from. A transaction that arrives after the drain waits for the next frame, so a late transaction draws one frame later and is never half-drawn. Frames that change the tree publish one `TreeBatch` (`State::take_tree_batches`). Tree work shares the 4 ms budget (`TREE_FRAME_BUDGET`): a transaction that starts after the budget is spent waits, whole, in order, for the next frame; the first transaction of a frame always runs. A frame draws with no shell attached. A transaction is checked against the batches published since its base serial when it applies, not when it was queued: a deferred transaction whose writes touch a node that a later batch changed is refused `stale-base` (`failed_op` names the first conflicting op), changes nothing and publishes nothing, while one that touches only other nodes applies in order. The rule is `gnoblin_render::tree_revision`, the same function `TreeSession::transact` calls, so the session and the frame cannot disagree. Node-core step 3, slice 6; section 4.5 (F6).
- The owner socket serves the tree (`gnoblin-compositor`, `ipc/tree_host.rs`, `ipc/tree.rs`). An owner connection attaches with `tree.attach` (version 1), is answered with its root and a snapshot of the scene, and transacts with `tree.transact`. One shell holds the tree at a time: a second attach while the first holds it is refused, and the hold is released when that connection closes. A transaction is applied whole or not at all; an applied transaction is answered on the reply and its changes are published as a `tree.changes` event at the new serial. A transaction before attach is refused. The owner is the connection with the `ReadConfig` capability. Calls and animations from an applied transaction are not dispatched yet, and the scene behind the host is a test implementation until the frame boundary (slice 6) supplies the real one. Node-core step 3, slice 5.

- The tree's frame boundary (`gnoblin-wayland`, `tree_frame.rs`). Each frame drains the transactions the shell queued through `TreeQueue`, in arrival order, before the composer draws, and applies each whole or not at all through `validate_and_apply` against the scene the composer draws from. A transaction that arrives after the drain waits for the next frame, so a late transaction draws one frame later and is never half-drawn. Frames that change the tree publish one `TreeBatch` (`State::take_tree_batches`). Tree work shares the 4 ms budget (`TREE_FRAME_BUDGET`): a transaction that starts after the budget is spent waits, whole, in order, for the next frame; the first transaction of a frame always runs. A frame draws with no shell attached. A transaction whose base serial is not the frame's starting serial is refused `stale-base` and changes nothing; this is the exact-serial rule `TreeSession::transact` uses. The section 4.5 per-id conflict rule (F6) is not implemented yet. Node-core step 3, slice 6.
- The `extensions/` directory holds out-of-process extension packages, each its own Cargo workspace excluded from the root workspace (`extensions/README.md`). `extensions/gnoblin-xr` is the scaffold for the XR extension (design/xr-extension.md, D34): the `xr-runtime` library finds the active OpenXR runtime by the loader's discovery rules (`XR_RUNTIME_JSON`, the XDG config dirs, `/etc/xdg`), detects `monado-service` and `wivrn-server` on `PATH`, and supervises the runtime service child with an on-failure restart policy (at most 3 restarts) and a clean stop on drop. No rendering and no layer submission yet.
- The replay harness (`crates/gnoblin-render/tests/replay.rs`) records a session of timed inputs (node transactions, frame ticks with `now`, scripted pointer events) and applies it through `validate_and_apply`. The tree hash is taken after every frame, and a session replays twice to the same per-frame hashes (F34). The session has a text format, documented in the module docs, that round-trips. Node-core step 3, slices 9 and 11 (part; the Lua parts are slice 10).
- Touchpad gestures reach the compositor. libinput swipe and pinch begin, update, end and cancel events keep their finger count, deltas and scale, and `Drm::dispatch` now delivers all libinput input to the host (previously it was pumped and never drained). A new `gnoblin-input` touchpad adapter turns samples into gesture events; `gnoblin-wayland` routes them to the `touchpad_gestures` bindings configured in Lua. Cancelled swipes, gestures on the lock screen, and gestures with no matching binding fire nothing; holds are dropped. Built-in `action` names are validated but have no executor yet, so only `command` bindings run. Covered by unit tests with synthetic samples; not yet verified on hardware.

- The tree transaction checks every property value against its schema type and refuses a wrong kind (`wrong-type`), an oversized text, byte string or list (`too-large`), and a non-finite number (`not-finite`). Node references name a live node of the property's class or a subclass. The catalog maps every tree property to a value kind and refuses to build for a schema type it cannot hold (node-core section 4.4a).
- The scene tree enforces ownership, id ranges and caps. Every node records its `owner` (the actor that created it) and `parented_by` (the actor that last parented it). `insert_as`, `remove_as` and `reparent_as` take the acting `Actor`: the shell may insert only ids below `COMPOSITOR_ID_BASE`, destroy only nodes it created (a subtree holding a compositor node is refused `NotOwner`), and move only unparented or shell-parented nodes. The node cap is `MAX_NODES` (65536), refused `TooManyNodes`; the depth cap is `MAX_DEPTH` (256), refused `TooDeep` on insert and on move. `remove` returns the removed subtree ids. Property writes are not governed by ownership. Node-api step 3, slice 3.
- Sampled curves: `SampledCurve` (`gnoblin-animation`) is a list of up to 1024 values evenly spaced over progress `[0, 1]`, interpolated linearly, validated when built (non-empty, first sample 0, last sample 1, finite, magnitude at most 1e6; overshoot between 0 and 1 is allowed). `TweenPlayer::start_sampled` and `retarget_sampled` play one, and `retarget` starts from the value on the node. The named easings are unchanged. Node-core step 3, slice 7.
- The node transaction (`gnoblin_render::transaction`): a batch of up to `MAX_OPS` (4096) ops `set`, `insert`, `destroy`, `call` and `new` is validated and applied as a whole. `validate_and_apply` works on a copy of the scene and swaps it in only when every op passes, so a refusal changes nothing; `Refusal` names the failed op index (`failed_op`, -1 when the batch is too large) and a kebab-case code from table 4.4. This slice emits `too-large`, `unknown-node`, `not-owner`, `root-immutable`, `cycle`, `unknown-class`, `unknown-member`, `wrong-type`, `read-only`, `not-animated`, `not-finite`, `out-of-bounds`, `out-of-range`, `bad-curve`, `bad-value`, `duplicate-node`, `too-many-nodes` and `too-deep`; the serial, IPC and paint codes (`stale-base`, `invalid-serial`, `shell-already-attached`, `not-privileged`, `bad-paint`) belong to later slices. Property names are checked against the `ClassInfo` trait, which a later slice implements from the schema catalog; the crate does not depend on `gnoblin-schema`. An animated `set` is validated and returned in `Applied` for the animation system; the scene is not written for it. Node-api step 3, slice 4.
- The schema format accepts `base` on an object (a class in the same namespace it inherits from; its properties, methods and signals come first in the derived class, and a property may not change type), `default` on a property (checked against its type), and `readonly` and `animated` booleans on a property (default false). Every existing schema parses unchanged. Node-core step 3, slice 1; the tree classes come in slice 2.
- The scene's paint and hit order is the sibling order: a node's position among its siblings is its paint order, last on top. `z_order` is removed from `NodeSpec`, and `set_z_order` and `set_z_orders` are replaced by `raise`, `lower`, `move_to`, `insert_at`, `reparent_at` and `set_order(parent, &[NodeId])`, which refuses a list that is not a permutation of the siblings. The composer no longer keeps a second stacking order. Node-api step 2 (D35).

The owner socket is the only transport, so the Lua stub, bindings and stock files leave the tree out. Node-core step 3, slice 2; the compositor does not serve these messages yet.

Its placement matches the 212 committed placement goldens, and `shell/init.lua` loads it, so the shell places new windows.
- The window manager accepts up to `MAX_WINDOWS` (256) windows. A window past the cap is refused with
  `TooManyWindows` before any state changes. Each provider in the layer registry has its own limit; extension
  providers keep the default of 32.
- Named workspace sets: the `workspace_sets` field of `gnoblin.configure` declares sets that name the workspace each

- The services role starts the GeoClue agent next to the polkit agent, with the policy of the `location` table

### Fixed

- Window rules now apply once a new window is on a desk, so a rule that sends it to another workspace takes effect.
  A rule that stops matching clears the field it set, such as `secure`, and a title change re-evaluates the rules.
- The Lua `core.insert` binding takes `(parent, node, index)`, the order `node.lua` calls it in. It had taken `(node, parent, index)`, so each child insert from `node.lua` swapped the parent and the child.

- The `gnoblinctl` and `gnoblin-wasm` catalogs leave out the owner-only `tree` namespace (`Catalog::load_dir_except(dir, &["tree"])`), as `gnoblinctl/build.rs` already did. Its `lock` and `destroyed` classes collided with the public ones, so `the_command_tree_matches_the_schema` and `the_generated_wit_matches_the_schema` failed. `gnoblin-schema/tests/owner_only_tree.rs` fails when any other crate loads the full catalog.

- Window records past the 32nd window do not trip a debug assertion, because the window manager's layer provider has
  its own limit.
- Pointer picking goes through the scene: a press or pointer motion over a window that the shell turned or moved
  reaches the window where it is drawn, not the unrotated rectangle it was placed in. Stacking ties still go to the
  last-drawn window.
- The composer's window nodes take their ids from `NodeIdAllocator` (`gnoblin-render`, `scene_ids.rs`), which starts at the compositor id base, never reuses an id and refuses exhaustion. Before, they started at 1, inside the shell's id range, so a shell node could collide with a window node (`duplicate-node`). A window whose node cannot be created is logged and not drawn, rather than dropped silently.

### Changed

- A window's `wp_alpha_modifier_v1` factor and the opacity a window rule sets fold into the window's scene node, as
  placement and shell opacity already do, so the composer draws the node's opacity alone. A closing window keeps the
  factors it had when its close fade began, as it already kept its placement and shell visuals: setting one during the
  close fade no longer changes the fade.
- Log records are written to `gnoblin.jsonl` in the state directory, one JSON object per line. `gnoblinctl log` and
  `gnoblinctl log --follow` read that file. The `gnoblin-store` crate, the SQLite log store, `gnoblinctl store`, the
  store IPC verbs and the `--store` flag are removed. `gnoblin.jsonl` and the legacy `store` files are not deleted.
- Log messages no longer start with a `[tag]` prefix. A crate's logger names its component, so a tag equal to
  that component is dropped, and any other tag becomes an `area = "tag"` field on the event. `xtask logging` fails a
  level macro whose message still starts with `[tag] `.
- Layouts with `extent = "unbounded"` must declare `kind = "tiling"`; a floating or kiosk layout that asks for it is
  refused when it loads. The wm now enforces `extent` when it settles a reply: a placement whose rectangle (before its
  transform) lies outside the output, or past the coordinate bound when unbounded, refuses the whole reply. The
  `carousel3d` layout declares `extent = "unbounded"`.

- Xwayland windows get Gnoblin's own frame, rules and effects like Wayland windows. Mutter no longer launches
  `mutter-x11-frames` or reparents X11 clients into frame windows. An X11 window that does not turn decorations off is
  framed under `frame.mode = "auto"` (the default for X11 when no rule sets a mode), `_GTK_FRAME_EXTENTS` feeds the
  visible bounds, `_NET_FRAME_EXTENTS` and `_NET_REQUEST_FRAME_EXTENTS` report Gnoblin's border, and Mutter's stock
  shadow no longer draws for managed X11 windows. A border change keeps the client where it is.
  `mutter-x11-frames` is no longer built or installed. A request for frame extents before the window exists is answered
  from the rules that match only the window type and `client_type`. The Mutter code for a frame window (`MetaFrame`,
  its sync counter and borders, the `_MUTTER_FRAME_FOR`, `_MUTTER_FRAME_EXTENTS` and `_MUTTER_NEEDS_FRAME` properties,
  and the frame mask in the X11 window actor) is removed in patch `11-window-frames/0011`.

      `<Shift><Control><Alt><Meta><Super><Hyper>`: `Shortcut.accelerator`, the `shortcut.bind`
      reply and the events use that form.
    - A pointer chord needs at least one modifier and ends with `Button1` to `Button3`.
    - An empty stylus keybinding still means none.
    - The four mechanisms stay, because they do different jobs. See
      [Which mechanism to use](docs/guides/shortcuts.md#which-mechanism-to-use).
- A Lua handler that throws now keeps running on later events. Before, Gnoblin disabled a `gnoblin.on`
  listener or an input handler after its first error, and an input handler that threw stopped the
  handlers after it. Now Gnoblin logs the error with the event name and the Lua stack, and every
  other handler of the event still runs. This applies to `gnoblin.on`, the `on` and `watch`
  callbacks of objects, `Process` and `Request` signals, `Operation` callbacks, tween callbacks and
  input handlers.
    - Each handler call has its own instruction budget, so a loop that never ends in one handler no
      longer makes the handlers after it fail.
    - An input handler that throws or returns an invalid value decides nothing, and only its own
      queued operations are dropped.
    - A handler that keeps failing is logged for its first three failures in a row and then once for
      every 1000. The user notice appears once for each run of failures.
    - See [Handler errors](docs/shell-api/errors.md#handler-errors).
- Shortcuts and launches are live objects in Lua; the functions that took IDs or tokens are gone
  (hard cutover; the wire names `shortcut.bind`, `shortcut.unbind`, `shortcut.session.end`,
  `launch.begin` and `launch.end` stay for socket clients, and no wire change was needed).
    - `gnoblin.shortcuts.bind(id, accelerator, options?)` returns a `Shortcut`: interned by ID,
      with `alive`, `on` and the signals `activated`, `deactivated`, `session_activated`,
      `session_key`, `session_ended` and `closed`. A refused binding ends at once and `closed`
      gets the reason.
    - `shortcut:unbind()` replaces `shortcuts.unbind(id)`, and `shortcut:end_session(session_id)`
      replaces `shortcuts.end_session(id, session_id)`: the shortcut owns the session.
    - `shortcuts.list()` now returns the shortcuts this runtime bound, as the same objects. The
      configured shortcut records move to `shortcuts.configured()`; the socket read
      `shortcuts.list` is unchanged.
    - `gnoblin.launches.begin(token, application, options?)` returns a `Launch` with `alive`,
      `on`, `watch` and the signals `changed`, `started`, `timed_out` and `closed`.
      `launch:finish()` replaces `launches.finish(token)`. `launches.list()` returns the same
      objects. A `Launch` has no link to a window or `Process`: the compositor does not record
      which window answered a launch.
    - `gnoblinctl lua` returns `Shortcut` and `Launch` records with the same methods.
- `gnoblin.input.select_source(type, id)` is gone from Lua: `InputSource:select()` replaces it.
  `input.sources()` and `input.current_source()` return `InputSource` objects, one for each type
  and ID, with `alive`, `on` and `watch` and the signals `changed`, `selected` and `closed`. The
  events `gnoblin.input.source-changed` and `gnoblin.input.sources-changed` move them. The wire
  method `input.select` stays; no API bump.
- A `Process` has `alive` and `on("closed", fn)`. The end signal is `closed`, as on Window,
  Workspace and Output, so code can treat every object alike; `status`, `exit_code` and `signal`
  say how it ended, and `wait()` and `kill()` stay.
- `gnoblin.session.suspend()`, `hibernate()`, `reboot()` and `poweroff()` finish with logind's real
  answer (bridge API 1.89). Gnoblin reads the capability (`CanSuspend` and its siblings), then asks
  logind for the action, and the Operation ends with `{accepted = true}` or with an error. See
  [session and runtime health](docs/shell-api/session-runtime.md).
    - `denied`: the capability answer is `no`, or logind or polkit refuses the action.
    - `unsupported`, `busy`, `unavailable`, `timed_out` and `internal` name the other failures.
    - The Lua runtime keeps running after the call. Before, the call stopped the runtime and the
      supervisor asked logind afterwards, so the Operation could not report a refusal.

- The orientation lock and the privacy screen use the new override call (bridge API 1.90). The
  Lua functions `gnoblin.input.set_orientation_lock(value)` and
  `gnoblin.outputs.set_privacy_screen(value)` are gone from Lua and from `gnoblinctl lua`. Use
  `gnoblin.settings.override("input.orientation_lock", value)` and
  `gnoblin.settings.override("monitors.privacy_screen", value)`, and `override:revoke()` in place
  of `"inherit"`. The wire methods `input.set_orientation_lock` and `monitors.set_privacy_screen`
  stay for socket clients, with two changes: a configuration reload that commits ends the value
  that a socket client set (the orientation lock already did), and `monitors.set_privacy_screen`
  fails with `true` or `false` when no output has a privacy screen. A newer value replaces an older
  one, whoever set it.

### Removed

- `window_management.new_window_placement` and `center-new-windows` are removed; a config that sets either is refused. The shell places new windows through `gnoblin.shell.floating` (`Floating`, `Cascade`, `Centred`). The Rust placement engine (`gnoblin-wm` `placement.rs`) is deleted; its golden cases stay as data in `tests/shell/placement_cases.toml`, generated by that engine at commit 370564286, and `crates/gnoblin-lua/tests/floating.rs` checks the Lua module against them.

- The external prompter for keyring unlock passwords is removed. The built-in keyring asks for its unlock password
  through the `prompt.secret` slot, like any passphrase request, and fails closed when no shell claims the slot. See
  `docs/shell-api/passphrase-prompts.md`.
- The `prompts` configuration section and its `prompts.enabled` key are removed. A configuration that sets them is
  refused when it loads. `keyring.enabled` still turns the built-in keyring on and off.
- The `when` key of `touchpad_gestures` entries is removed, with its `"unlocked"`, `"locked"` and `"any"` values and the
  legacy `"normal"` and `"unlock-screen"` spellings. A configuration that sets `when` is refused when it loads. Gesture
  bindings run only while the session is unlocked and never reserve a gesture on the lock screen, so a binding meant for
  the lock screen can no longer be written. Gestures there are left to the lock screen client.

### Fixed

- A `config.commit` that removes window rules is answered only after the compositor loop has applied the removal. Before,
  a window the client mapped right after the answer could still be placed under the removed rule, for example maximised
  at the output size, depending on the order the loop drained its queues.

### Added

- `gnoblin.input.grab(options?)` takes the keyboard and returns a live `Grab` (bridge API 1.91). See
  [keyboard grabs](docs/shell-api/input-grab.md). Before, the only keyboard capture was the
  shortcut session of a `modal` or `capture_input` shortcut: one slot, a fixed 10 second timer,
  and key events without text.
    - The grab is a lease. It expires after `timeout` idle seconds (1 to 60, default 10) unless
      `grab:renew()` runs or a key event arrives; each key event starts the timeout again, because
      someone who types still needs the grab.
    - `grab:on("key", fn)` gets `{key, keysym, keycode, modifiers, pressed, repeated, text,
composing, time}`. `text` is the character a press types. Gnoblin feeds each press to the
      compose table of the locale (xkbcommon), so a dead key or a Compose sequence gives one
      composed character on the key that completes it, and `composing` is true inside the sequence;
      a key that breaks the sequence has its own text.
    - `grab:on("closed", fn)` gets the reason: `released`, `expired`, `replaced` (a second grab
      takes the one slot), `locked`, `preempted` (Mutter gave the keyboard to a popup or other
      grab), `config_reloaded`, `runtime_stopped`, or the message of the compositor when it refused.
    - The grab refuses to start while the session is locked and ends when it locks. It never takes
      the keyboard from a shortcut session or `shortcuts.capture`, and they cannot start while it
      holds the keyboard. Its events carry no `focus_context`.
    - The grab refuses to start while any key is down. Mutter gives the release of a held key to
      the grab, so the focused application, which saw the press, would never see the key lift.
      The refusal names the held key. Start a grab from a key release or a later event.
    - Shortcut sessions keep their fixed 10 second timer. It guards a user gesture against a lost
      key release and nothing owns it, so nothing can renew it; a script-renewed lease would let
      a script hold a session open, and a grab that carries a `focus_context` would let a script
      move windows without a gesture.
    - `gnoblin.input.grab` raises an error in `gnoblinctl lua`: a console script has no runtime
      to receive keys.
- `gnoblin.settings.override(path, value)` and `window:set_effect(name, value)` return a live
  `Override` that layers a value over the committed configuration, or an effect over the window
  rules of one window, until it is taken back (bridge API 1.90). See
  [overrides](docs/shell-api/overrides.md).
    - Settings that can change at runtime are `window_management.*`, `compositor.*`,
      `cursor.theme`, `cursor.size`, `layer_shell.preserve_active_window`,
      `monitors.privacy_screen` and `input.orientation_lock`. Any other path raises an error that
      says why it cannot change. The value is checked as the configuration checks it.
    - The effects are those of window rules: `opacity`, `blur`, `blur_ignore_shadows`, `shader`,
      `shader_uniforms`, `frame` and `corners`. The effect goes over the matching rules as one more
      rule and changes only what it sets.
    - `override:revoke()` returns the target to the next older layer, and
      `override:on("closed", fn)` gets the reason: `revoked`, `replaced`, `window_closed`,
      `config_reloaded` or the compositor's message.
    - The latest override of one setting, or of one effect of one window, wins; the older one ends
      with `replaced`. A reload, a Lua worker restart and the close of the window end overrides.
    - `gnoblin.settings` keeps showing the committed values.
- Outputs are live objects (bridge API 1.88). See [outputs](docs/shell-api/outputs.md).
    - Every read of one display returns the same `Output`, with `alive`, `on` and `watch`.
    - An output also has its logical monitor's index, size and work area, and its privacy
      screen state.
    - The privacy screen request covers the whole session, because the compositor keeps one request and applies it
      to every output that has a privacy screen. An `Output` has no method for it.
      `output.privacy_screen` and `output:watch("privacy_screen", fn)` read the state. Bridge API 1.90 replaced
      the first write call, `gnoblin.outputs.set_privacy_screen(value)`, with
      `gnoblin.settings.override("monitors.privacy_screen", value)`. The wire call
      `monitors.set_privacy_screen` is unchanged.
    - New events tell Lua and shell processes when a display is added, changes or is removed.
    - Monitor events and monitor reads stay for shell processes only.
- `gnoblin.idle.watch(seconds)` returns a live `IdleWatch` for any idle time from above 0 up to
  86400 seconds, with `alive`, `idle`, `seconds`, `on("idle" | "active" | "closed")`, `watch` and
  `cancel()`. Each runtime can have up to 256 watches. A reload ends every watch. See
  [idle watches](docs/shell-api/idle.md).
- The `gnoblin.location.authorization-finished` event (bridge API 1.87) reports how each location
  request ended: `allowed`, `denied` or `timeout`. A Lua location `Request` now finishes from it,
  so `finished()` reports the real outcome when a shell process answered the request instead of
  `timeout`.
- Lua timers and Operation methods. `gnoblin.timers.after(seconds)` returns an Operation that
  succeeds after the given time, and `gnoblin.timers.now()` reads a monotonic clock. Every
  Operation now has `map(fn)`, `timeout(seconds)` and `cancel()` beside `on_complete`. Pending
  timers end when the config reloads and do not delay the reload. See
  [operations, errors and timers](docs/shell-api/errors.md).
- `gnoblin.process.spawn(argv, options?)` starts a program and returns a `Process` with its
  `pid` and `status`, `wait()` for its exit and `kill(signal?)`. Options set the working
  directory, environment, standard input, where each output stream goes and how much of it to
  capture, and a timeout. Output is returned as raw bytes. A process keeps running across a
  config reload. See [processes](docs/shell-api/processes.md).
- Window records carry `pid`, the client's process ID from the display server, and `process`,
  the `Process.id` when `gnoblin.process.spawn` started the program. `window:present()` focuses
  such a window without a key press, after the user has not typed or clicked for 250 ms. A
  shell can now open a passphrase prompt that takes typing straight away. See
  [focus and activation](docs/shell-api/focus-activation.md).
- Keyring and GPG prompts, polkit authentication, location authorization and session-lock
  requests reach Lua as one `Request` object, `event.request`. It has `id`, `kind`, `status`,
  the request's detail fields and `finished()`, an Operation that succeeds once with the
  outcome. `answer()`, `cancel()`, `claim()` and `on()` exist only on the kinds that use them.
  See [requests](docs/shell-api/requests.md).
- The Lua configuration receives `gnoblin.session.lock-requested` when it listens for it, so
  a config can start a locker without a separate shell process. See
  [session lock](docs/session-lock.md).
- Windows, workspaces and layer surfaces are live objects in Lua. Every read of one returns
  the same object, updated with each change, with `alive`, `on(signal, fn)` for its
  `changed`, `closed` and other signals, and `watch(field, fn)` for one declared field. Before,
  each read returned a detached copy. See [live window objects](docs/shell-api/windows.md#live-window-objects).
- `window:set_opacity`, `set_scale`, `set_rotation`, `set_offset` and `reset_visuals` change
  how the compositor draws a window without moving its frame. Clicks follow the drawn
  position, a config reload resets them, and they fail while the session is locked. Window
  objects show the values in `opacity`, `scale`, `rotation` and `offset`, and `gnoblinctl lua`
  has the same methods. See
  [change how a window is drawn](docs/shell-api/windows.md#change-how-a-window-is-drawn).
- `gnoblin.tween()` builds a timeline of window opacity, scale, rotation and offset changes,
  intervals and callbacks, and the compositor plays it in its render loop. `play`, `pause`,
  `seek` and `kill` control it; a reload or a session lock cancels it. `gnoblin.ease` and
  `gnoblin.lerp` give the same easing math in Lua. See [tweens and easing](docs/shell-api/tweens.md).
- Packages for Debian testing (`.deb`) and Alpine edge (`.apk`, release assets only), and arm64
  builds of every package. A single build
  now writes the rpm, deb, Arch and tar packages: `scripts/build-prefix.sh` builds Gnoblin
  into a prefix and pkgsmith writes the packages from it with the definitions in `pkgsmith/`.
  See [packaging and releases](docs/distribution.md).
- Signed package repositories for Fedora, openSUSE Tumbleweed, Debian testing and Arch, each with
  a `stable` and a `nightly` channel. A release tag publishes the stable channel.
  A daily build of the main branch publishes the nightly channel when main has
  moved. `scripts/pkgrepo` builds, signs and uploads the repositories, and
  `design/package-repositories.md` describes the layout. See
  [package repositories](docs/package-repositories.md).
- A small notice at the top centre of the screen when a config reload finishes (`Config reloaded`,
  gone after about 2 seconds), when a reload is rejected (the first line of the error, until it is
  clicked or a reload succeeds), and when a shortcut or command does not start
  (`<name> could not start: <reason>`). See
  [reload and error notices](docs/guides/files_and_load_order.md#reload-and-error-notices).

- System drop-ins load on their own. Lua files in `gnoblin/conf.d` under each `XDG_DATA_DIRS` entry
  (such as `/usr/share/gnoblin/conf.d`) and in `/etc/gnoblin/conf.d` run before your `init.lua`, or
  after the built-in defaults when you have no `init.lua`, so a package no longer needs a `gnoblin.load`
  line in your config. A drop-in that fails is skipped and shown in the recovery notice. See
  [system drop-ins](docs/guides/files_and_load_order.md#system-drop-ins).

### Fixed

- `gnoblin.input.grab` was refused for ever, naming a key that was up, after the release of that key was swallowed.
  The compositor refuses a grab while a key is held and tracked the held keys behind the diagnostic console, which
  takes every key while it is open: a key pressed before the console opened and released under it stayed held until
  the user tapped it again. Held keys are now tracked ahead of the console (Mutter patch
  `0132-track-held-keys-before-the-console`), so a key released under the console is up, and a key pressed under it
  and still down afterwards refuses a grab until it lifts. Held keys are kept per keyboard, and a keyboard that is
  removed drops the keys it held, so the removal of a device with a key down no longer refuses grabs. The refusal
  for a key that is really down is unchanged.
- A playing tween held a configuration reload back for 15 seconds, and the reload then failed. A reload now waits
  for every other pending operation but not for a tween. The compositor stops the tween when the new configuration
  takes effect, the `Operation` of `play()` succeeds with the outcome `"cancelled"`, and the `"closed"` signal of
  the `Tween` runs with the reason `"config_reloaded"`. A reload that fails leaves the tween playing.
- `gnoblin.workspaces.create`, `next`, `previous` and `Workspace:activate` and `rename` resolved to a plain record
  with a `windows` key. They resolve to the live `Workspace` that `gnoblin.workspaces.by_id` returns, with
  `window_count`.
- A `gnoblin.configure` call that the validator rejected inside an `Operation` callback failed its `Operation` and
  also logged `deferred Lua operation callback failed`. It fails the `Operation` only.
- `gnoblinctl config reload` accepted `input.keyboard.xkb_options = {"caps:escape"}` in the first
  load but refused it on reload with `input.keyboard.xkb-options: invalid value`, because the
  second normalisation of the input document read only the unnormalised string list. The same code
  is on `main`. A reload now keeps the option.
- The portal backend now destroys and releases each ScreenCast consent dialog
  and its hidden parent window when the session ends. Before, the dialog's
  widget tree stayed alive after every screen cast.
- The Lua API reference now describes `gnoblin.windows.focused`, `windows.by_id`,
  `windows.snap_context`, `gnoblin.outputs.*`, and `gnoblin.capabilities.list`.
  These functions already worked, but editor hints and the generated
  `gnoblin.d.lua` did not list them.
- The Lua API reference no longer lists `Window:match`. The runtime never installed it; the
  window-rule fields stay available from `gnoblinctl window match`.
- A callback added with `Operation:on_complete` after the operation had finished now runs.
  Before, the runtime called the Operation table instead of the callback and logged an error.
- A shell process that called `prompt.respond`, `prompt.cancel`, `auth.*` or
  `location.authorize_app` could answer a request that it never received. The call reached
  the compositor without the client's identity, so the recipient check did not run. The
  compositor now checks it.
- The `monitor.list` bridge method failed with "Lua monitor record has no integer index". The
  reply now lists each monitor again.

### Migration

1. Remove the `permissions` section, `gnoblin.permission_rule` calls, and
   `gnoblin.portals.grants` calls from your Lua config. A `permissions`
   section is ignored and the log names it as an unknown section. A call to a
   removed function is a Lua error and the config fails to load.
2. Write permission rules in the portal backend you use. Bingux reads its own
   rules.
3. Stop subscribing to the removed events and calling the removed commands.
4. Replace `gnoblin.commands.run` and `gnoblin.commands.capture` with
   `gnoblin.process.spawn` as the table above shows.
5. Answer prompts, authentication and location requests through `event.request`, as the
   table above shows.
6. Rewrite table calls to the positional forms above, and replace the removed duplicate
   names.

### Changed

`org.gnoblin.Shell.GlobalShortcutsProvider` `BindShortcuts` and
`ConfigureShortcuts`, and `org.gnoblin.Shell.GlobalShortcutsRebind`
`RebindShortcuts`, take a trailing request handle (`o`), the caller's
`org.freedesktop.portal.Request` object path. The shell uses it, with the
application ID, to identify the requester. Calls with the old argument lists
are not supported. Deploy the portal backend and the shell provider together.
